## テスト戦略の全体像

**ホスト PC で回るテストを最大化し、実機テストを「実機でしか確認できないこと」に絞る。** これは開発ループを速く保つための基本方針である。ドメインロジック・永続化フォーマット・ジェスチャー計算の純関数部分はすべてホスト PC 上でテストし、画面描画・タッチ入力・振動・バッテリーなど物理ハードウェアに依存する検証のみを実機で行う。

テストは以下の 4 階層で整理する。

| 階層 | 名称 | 実行環境 | 対象 |
|------|------|---------|------|
| L1 | ホスト単体テスト | ホスト PC（`pio test -e native`） | ドメインロジック、永続化レコードのシリアライズと CRC、ジェスチャー角度計算の純関数部分 |
| L2 | 実機ユニット／疎通テスト | M5Stack StopWatch 実機 | 画面描画、タッチ入力、ボタン、振動、バッテリー取得、PSRAM 確保 |
| L3 | 実機シナリオテスト | M5Stack StopWatch 実機 | 連続操作、電源断、長時間稼働 |
| L4 | 運用テスト | 実機 + 実環境 | 大会想定での視認性、公平性、運用手順 |

---

## L1: ドメイン単体テスト

ドメインロジックの正当性を検証するテストである。各テストは [ドメインモデル](./06-domain-model.md) で定義される不変条件を守ることを確認する。

| テスト | 期待結果 | 対応する不変条件 |
|--------|---------|----------------|
| 40に-1 | 39 | ライフ変更が正しく適用される |
| 0に-1 | 0 | ライフは 0 未満にならない（0 クランプ） |
| 40に+10 | 50 | 開始ライフを超えて増加できる |
| 2に-5 | 0、適用差分は-2 | `appliedDelta` と `requestedDelta` が正しく記録される |
| 上記をUndo | 2 | Undo は `before` 値へ戻す（`requestedDelta` の逆ではない） |
| 長押し（スライド）で-8後にUndo | 長押し開始前へ戻る | 1 回のスライド全体が 1 件として履歴登録される |
| 履歴65件 | 最新64件だけ残る | `RingBuffer<LifeChange, 64>` の容量制約 |
| UINT32_MAX付近で加算 | オーバーフローしない | `int64_t` キャストによるオーバーフロー防止 |
| 上下交換 | ライフと開始値が正しく交換される | Swap Sides の整合性 |

## L1: ジェスチャーのテスト

外周スライド方式の角度計算に関する純関数部分のテストである。ハードウェア非依存で実行できる。

| テスト | 期待結果 |
|--------|---------|
| 角度累積の境界またぎ（±pi をまたぐ） | `normalizeDelta()` により正しく補正され、不連続なジャンプが発生しない |
| 最低移動角 6 度未満 | ライフ変更が発生しない（`previewSteps` が 0 のまま） |
| 方向反転（反時計回り 5 段階 → 時計回り 2 段階戻す） | -3 で確定される（1 件として記録） |
| 角速度しきい値以上のジャンプ（`abs(deltaDeg) / deltaMs >= 0.7`） | そのサンプルが無視され、累積角度に加算されない |
| サンプル間隔が大きく空いた場合の正当な操作（例: 270 ms 欠測後の 63 度変化） | 角速度が正常範囲（0.7 度/ms 未満）であれば棄却されず、累積角度に正しく加算される |
| 中央引き込み（半径 145px 未満への移動） | 操作がキャンセルされ、ライフ変更なしで `Idle` 状態に戻る |
| 10 度移動ごとに 1 ライフ変動 | 累積角度 30 度で +3 または -3 が正しくプレビューされる |
| 上側プレイヤー領域（上側 140 度: 200 度〜340 度）で開始 | `PlayerId::Top` が選択される |
| 下側プレイヤー領域（下側 140 度: 20 度〜160 度）で開始 | `PlayerId::Bottom` が選択される |
| 開始禁止領域（左右各 20 度）で開始 | ジェスチャーが開始されない |

## L1: 永続化テスト

`PersistentRecord` のシリアライズ・デシリアライズと CRC 検証の正当性を確認する。

| テスト | 期待結果 |
|--------|---------|
| 再起動後の復元 | 最新の正常なスロットから `MatchState` が正しく復元される |
| CRC 破壊後のフォールバック | CRC が不一致のスロットをスキップし、1 つ前の正常なレコードへフォールバックする |
| 旧 `schemaVersion` の読み込み | 対応範囲内の旧バージョンを正しくマイグレーションして読み込める |
| 未対応 `schemaVersion` の安全な拒否 | 対応範囲外のバージョンを検出した場合、データを破壊せず安全にデフォルト状態で起動する |
| 書き込み途中でも起動不能にならない | 16 スロットローテーションにより、書き込み途中のスロットが存在しても別の正常なスロットから起動できる |

## L1: Haptics テスト

振動制御ロジックの正当性をホスト PC 上で検証する。振動ハードウェアの呼び出しはモック化し、`setVibration()` の呼び出し引数とタイミングを検証する。

| テスト | 期待結果 |
|--------|---------|
| 指定時間経過後に `setVibration(0)` が呼ばれる | 振動開始から指定時間（例: 20 ms）経過後に `setVibration(0)` が呼ばれ、振動が停止する |
| `setVibration(0)` の呼び忘れがない | すべての振動パルスの開始に対して、対応する `setVibration(0)` が必ず呼ばれる |
| 間引きロジックが連続するライフ段階に対して正しくパルスを減らす | N 段階に 1 回のみ振動パルスが発生し、残りの段階では振動が発生しない（間引き方式が未決定のため、方式確定後にテストケースを具体化する） |
| ライフ 0 到達時の警告振動は間引きの対象外 | ライフ 0 に到達した場合、間引き状態に関わらず必ず長い振動パルスが発生する |

> **注記**: 間引きの具体的な方式（パルス間引き vs 感度見直し）は未決定である（ADR-17）。方式確定後にテストケースを具体化する必要がある。

## L2: 実機入力テスト

実機のタッチスクリーン・ボタン・振動モーターを使った検証である。

| テスト | 期待結果 |
|--------|---------|
| 毎秒 5 回の操作で欠落・二重入力なし | すべての操作が正確に 1 回ずつ処理される |
| 外周スライドの検出精度 | 外周操作リング（半径 170〜225px）内でのスライドが正しく検出される |
| 領域またぎドラッグ | 操作開始後に上下境界を越えても対象プレイヤーが変更されない |
| 中央帯接触 | 表示領域（半径 0〜169px）へのタッチで操作が発生しない |
| ロック中 100 回タッチ | タッチロック中にタッチ入力が完全に無効化される（物理ボタンは有効） |
| 台座から動かない | 操作中に卓上台座から本体がずれない |

Phase 0 での計測項目（`atan2()` の符号確定、描画レート、PSRAM 上の `M5Canvas` 確保サイズ）については [開発ワークフロー](./03-dev-workflow.md) を参照のこと。

### L2: 描画レートの回帰確認

部分再描画方式（ADR-15）の採用に伴い、描画処理が 43 ms の描画予算内に収まり続けることを実機で定期的に確認する。

| テスト | 期待結果 |
|--------|---------|
| ライフ数値の部分再描画が 43 ms 以内に完了する | 部分再描画の所要時間が外周スライド操作中のライフ更新間隔（約 43 ms）を超過しない |
| 画面遷移（全画面再描画）が体感上スムーズである | 全画面転送の所要時間（約 45 ms）で画面遷移が完了し、操作の阻害にならない |

## L3: 電源断テスト

各処理の境目で強制的に電源を落とし、データの整合性と復元性を検証する。

| 電源断タイミング | 検証内容 |
|-----------------|---------|
| イベント生成前 | 操作が未記録のまま安全に起動できる |
| 書き込み途中 | 書き込み中のスロットが破損しても他のスロットから復元できる |
| flush 直後 | flush されたデータが正しく永続化されている |
| 状態反映直後 | RAM 上の状態と永続化データが一致する |
| NVS 更新途中 | NVS ローテーションにより前のスロットから復元できる |
| 試合終了処理途中 | 試合状態が不整合にならず、再起動後に安全に復帰できる |

**合格基準: 許容するのは「確定途中だった最後の 1 操作が未適用になること」のみ。** それ以前に確定済みの操作がすべて保持され、起動不能にならないことを必須とする。

## L3: 長時間・耐久テスト

### 連続稼働時間の実測

測定条件: 無線無効・輝度 30〜40%・振動有効。
バッテリー容量 450mAh に対し、最低目標は連続 4 時間、推奨目標は連続 8 時間である。実測値は要実機確認。

### 連続ランダム操作テスト

1000 回の連続ランダム操作（外周スライド、Undo、タッチロック切り替え、メニュー操作）を実行し、ドメインモデルの状態と画面表示が一致することを検証する。

## L4: 大会利用テスト

Flesh and Blood の大会環境を想定した運用テストである。

| テスト | 期待結果 |
|--------|---------|
| 60〜80cm から数字を読める | 対面のプレイヤーがライフ値を視認できる |
| Wi-Fi・Bluetooth が起動していない | Tournament Mode で無線機能が完全に無効化されている |
| 1 操作でリセットできない | Rematch・New Game には長押し確認が必要 |
| 履歴を双方から確認できる | 上下どちらのプレイヤーからも変更履歴を確認できる |
| 低バッテリーでもライフ表示が失われない | バッテリー警告を表示しつつライフ値の表示を維持する |

## テスト実行方法

### ホストテスト（L1）

```bash
pio test -e native
```

### 実機テスト（L2〜L4）

実機テストの前提条件（環境構築、書き込み手順、USB 接続の注意点）は [開発環境](./02-dev-environment.md) を参照のこと。

#### 実機テストの実務メモ（Phase 0 で判明: 2026-08-17）

- **`pio device monitor` は TTY を要求する。** 非対話環境（CI、IDE のターミナルパネル等）では `termios.error: (19, 'Operation not supported by device')` で失敗する。シリアル出力の確認には pyserial (`serial.Serial`) で直接ポートを開いて読む必要がある。
- **診断スケッチは `loop()` から定期出力にする。** Native USB-CDC ではチップのリセットで USB が再列挙され、開いていたポートハンドルが無効になる。`setup()` で 1 回だけ出力するスケッチでは出力を取りこぼしやすい。`loop()` から 1〜2 秒間隔で繰り返し出力する作りにすることで、ポート再接続後に確実にデータを受信できる。

## カバレッジ方針

- **ドメイン層**: 網羅を目指す。ライフ変更・Undo・履歴管理・ジェスチャー角度計算・永続化レコードのシリアライズなど、ハードウェア非依存のロジックはすべて L1 テストでカバーする。
- **ハードウェア依存層**: 疎通確認にとどめる。画面描画・タッチ入力・振動・バッテリー取得などは L2 テストで基本動作を確認し、詳細な品質検証は L3・L4 で補完する。
