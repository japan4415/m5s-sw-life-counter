## レイヤ構成図

依存方向は上から下への単方向のみである。下位レイヤが上位レイヤを参照することはない。

```
┌───────────────────────────────────┐
│ AppController                     │
│ 画面状態・コマンド振り分け         │
├───────────────────────────────────┤
│ MatchModel          InputController │
│ LifeService         GestureDetector │
├───────────────────────────────────┤
│ Renderer            Storage        │
│ Haptics             PowerManager   │
├───────────────────────────────────┤
│ M5Unified / M5GFX                  │
├───────────────────────────────────┤
│ M5Stack StopWatch Hardware         │
└───────────────────────────────────┘
```

### 各層の責務

| レイヤ | 責務 |
|---|---|
| AppController | アプリケーション状態の管理、画面遷移制御、入力イベントの振り分け |
| MatchModel / LifeService | ドメインロジック（ライフ変更、Undo、履歴管理）。ハードウェア非依存 |
| InputController / GestureDetector | タッチ入力の受信、極座標変換、外周スライドジェスチャーの検出、サンプル間経過時間に基づく角速度異常値判定。ジェスチャー検出ロジック自体はハードウェア非依存 |
| Renderer | M5GFX を使った画面描画。PSRAM 上の Canvas への描画と転送 |
| Storage | NVS への永続化（MVP）。保存スケジューリングとスロットローテーション |
| Haptics | 振動モーターの制御。パターン再生とタイミング管理 |
| PowerManager | 画面輝度制御、スリープ管理、バッテリー状態監視 |
| M5Unified / M5GFX | ハードウェア抽象化ライブラリ。ディスプレイ・タッチ・ボタン・振動・電源を統一的に扱う |
| Hardware | M5Stack StopWatch の物理ハードウェア（ESP32-S3、AMOLED、タッチ IC、振動モーター等） |

## メインループ

```cpp
void loop() {
    M5.update();
    inputController.poll();
    while (inputController.hasEvent()) {
        const InputEvent event = inputController.nextEvent();
        appController.handle(event);
    }
    haptics.tick();
    storage.tick();
    powerManager.tick();
    renderer.renderIfDirty();
}
```

### delay() を使わない非ブロッキング設計

メインループでは `delay()` を一切使用しない。各サブシステム（描画、振動、保存、電源管理）が `tick()` メソッドで非ブロッキングに処理を進める。

この設計を採用する理由:

- **描画と振動が互いをブロックしない** -- 振動パターン再生中でも画面更新が止まらない
- **保存処理がユーザー操作を妨げない** -- NVS 書き込みは `storage.tick()` 内でスケジューリングされ、入力処理を遅延させない
- **電源管理が即座に反応できる** -- 無操作タイムアウトやバッテリー監視が毎ループで評価される
- **入力イベントの取りこぼしを防ぐ** -- `delay()` で CPU を占有しないため、タッチイベントを確実に処理できる

時間管理には `millis()`（または ESP-IDF の単調増加タイマー）を使用し、各サブシステムが前回の処理からの経過時間を自分で判断して動作する。

## 入力パイプライン

タッチ入力からドメインモデル更新・再描画までの処理フローを以下に示す。

```
タッチ座標（M5.Touch）
  │
  ▼
GestureDetector
  ├─ 極座標変換（dx, dy → radius, angle）
  ├─ 外周リング判定（radius >= 165px、上限なし）
  ├─ プレイヤー選択（タッチ開始の Y 座標）
  ├─ 角度累積と normalizeDelta
  ├─ サンプル間経過時間に基づく角速度異常値判定
  └─ GestureState 遷移（Idle → Candidate → Active → 確定/Cancelled）
  │
  ▼
InputEvent（ライフ変更要求 / Undo / ロック / メニュー）
  │
  ▼
AppController
  ├─ 画面状態に応じたイベント振り分け
  └─ LifeService 呼び出し
  │
  ▼
LifeService
  ├─ applyLifeChange / commitGesture
  ├─ 履歴への登録
  └─ MatchState 更新
  │
  ▼
再描画要求（dirty フラグ）
  │
  ▼
Renderer（次の loop() で renderIfDirty）
```

物理ボタン入力（Button A: Undo、Button B: タッチロック、A+B 長押し: メニュー）も `InputController` を通じて同じ `InputEvent` として `AppController` に渡される。

## 描画方式

LVGL は使用せず、M5GFX で直接描画する。

### 全画面バッファの配置（Phase 0 Step 6 実測で確認済み）

468 x 468 x 2 bytes の全画面バッファを **PSRAM 上の `M5Canvas`** に確保する。Phase 0 Step 6（2026-08-17）の実測結果:

| 項目 | 値 |
|------|------|
| 実消費メモリ | 438,068 bytes（設計上の期待値 438,048 bytes とほぼ一致。20 bytes の差はアロケータのヘッダ） |
| 確保後の空き PSRAM | 7,509,919 bytes（約 7.16 MiB） |

全画面 Canvas の PSRAM 上への確保は問題なく成立する。

### 180 度回転描画（Phase 0 Step 7 実測で確認済み）

上半分の 180 度回転描画が正しく表示されることを実機の目視で確認した（2026-08-17）。

### 描画レート実測（Phase 0 Step 8、2026-08-17）

| 方式 | 転送サイズ | min (us) | median (us) | max (us) | FPS |
|------|-----------|----------|-------------|----------|------|
| 全画面 468x468 | 438,048 B | 44,610 | 44,639 | 45,236 | 22.4 |
| 上半分 468x234 | 219,024 B | 22,299 | 22,312 | 22,848 | 44.8 |
| 中央 200x120 | 48,000 B | 4,993 | 4,994 | 5,555 | 200.2 |

### 描画方式の候補と決定

| 方式 | 内容 | 転送時間 | 備考 |
|------|------|---------|------|
| 1. 全画面 Canvas 転送 | 画面更新時に全画面 Canvas へ描画し、一括転送する | 44.6 ms | 実装は最もシンプルだが、**実測により描画予算を超過するため MVP で不採用** |
| 2. 分割 Canvas | 上半分・中央・下半分を個別の Canvas に分割する | 22.3 ms（半分転送時） | 全画面より改善するがまだ余裕が小さい |
| 3. 変更領域のみ再描画 | 変更されたプレイヤー領域だけを再描画・転送する | **5.0 ms**（中央 200x120 相当） | **MVP で採用** |

**MVP は方式 3（変更領域のみ再描画）を採用する。** 方式 1（全画面 Canvas 転送）は Phase 0 Step 8 の実測により否定された。

**構成**: 全画面 Canvas は PSRAM 上に保持し、描画先バッファとして使用する。ただしディスプレイへの転送は変更のあった部分矩形のみを `pushSprite()` で行う。これにより全画面 Canvas の利便性（任意の座標への描画、回転描画のソースとしての利用）を維持しつつ、転送コストを抑える。

### 描画予算

外周スライド中はライフ表示が約 43 ms ごとに更新される（感度 10 度/ライフ、スイープ角速度 233 度/秒の実測に基づく）。描画に使える時間はこの 43 ms からタッチ処理・振動制御等の時間を差し引いた残りである。

| 方式 | 転送時間 | 43 ms に占める割合 | 判定 |
|------|---------|-------------------|------|
| 全画面 468x468 | 44.6 ms | 103%（予算超過） | 不可 |
| 中央 200x120 | 5.0 ms | 11.6% | 十分な余裕あり |

方式 3 であれば描画転送後にも約 38 ms の余裕があり、タッチ処理・振動制御・保存スケジューリングを十分に収容できる。

## ハードウェア抽象化

以下のハードウェア依存コンポーネントを薄いインターフェースで包み、テスト時はフェイク実装に差し替える:

| インターフェース | 実装（本番） | 責務 |
|---|---|---|
| `Haptics` | `haptics_m5.cpp` | 振動モーターの制御。強度 255 固定の PWM パルスを非ブロッキングで再生し、間引きロジックを管理する |
| `PowerManager` | `power_m5.cpp` | 画面輝度制御、スリープ遷移、バッテリー状態取得 |
| `Storage` | `storage_nvs.cpp` | NVS への永続化。スロットローテーションと CRC 検証 |
| `Display` | M5GFX / M5Canvas | 画面描画と部分矩形転送 |

この抽象化により、ドメインロジック（`domain/`）とジェスチャー検出ロジック（`input/` の純関数部分）を実機なしでテストできる。テスト時には各インターフェースのフェイク実装（呼び出し記録のみを行うスタブ等）を注入する。

### Haptics コンポーネントの責務（Phase 0 Step 5 実測に基づく具体化）

`M5.Power.setVibration(uint8_t level)` は強度指定（0〜255）であり、時間指定ではない。`level` を書くとモーターが回り続け、`setVibration(0)` を書くまで停止しない。したがって `Haptics` コンポーネントが以下の責務を担う:

1. **パルス開始**: `M5.Power.setVibration(255)` を呼び出す。強度は 255 固定（実測で 32〜192 は体感できないため）
2. **経過時間の監視**: `tick()` 内で `millis()` を用いてパルス開始からの経過時間を確認する。所定の時間（パターンごとに異なる）が経過したら `setVibration(0)` で停止する
3. **パターン管理**: 複数パルスのシーケンス（例: キャンセル振動 = 20ms ON → 60ms OFF → 20ms ON）を状態マシンで管理する
4. **間引きロジック**: 連続するライフ段階変化に対してパルスを間引く。高速スライド時のデューティ比が過大になるのを防ぐ（詳細は [UI/UX 設計](./05-ui-ux.md) の振動フィードバック設計節を参照）

`haptics.tick()` はメインループの毎反復で呼ばれる必要がある。`delay()` は一切使用しない。

## 状態管理

アプリケーションは **アプリ状態** と **電源状態** の 2 軸を直交して管理する。

### アプリ状態

| 状態 | 意味 |
|---|---|
| `BOOT` | 起動直後。NVS の読み込みと復元判定を行う |
| `RESTORE_PROMPT` | 保存済みゲームが見つかった場合の復元確認画面 |
| `SETUP` | 初期ライフ設定画面 |
| `ACTIVE` | ゲーム進行中。外周スライドによるライフ変更を受け付ける |
| `LOCKED` | タッチロック中。タッチ入力は無効だが物理ボタンは有効 |
| `MENU` | ゲームメニュー表示中 |

### 電源状態

| 状態 | 意味 |
|---|---|
| `NORMAL` | 通常輝度で表示中 |
| `DIMMED` | 無操作タイムアウトにより低輝度へ減光 |
| `SCREEN_OFF` | セットアップ中の長時間無操作により画面消灯 |

これらの 2 軸は独立して遷移する。例えば、`ACTIVE` 状態で `DIMMED` に遷移しても、入力が発生すれば `NORMAL` に復帰しつつその入力も処理する。

各状態の遷移条件と詳細は [UI/UX 設計](./05-ui-ux.md) と [電源・大会利用](./09-power-and-tournament.md) を参照。

## 並行性の方針

### MVP: 単一ループ

MVP では単一の `loop()` 関数で全処理を実行する。複雑なマルチタスク構成は不要と判断されている。理由は以下の通り:

- 描画・入力・振動・保存・電源管理のいずれも `tick()` ベースの非ブロッキング設計であり、互いを待たない
- NVS 書き込みは非同期スケジューリングで処理され、ユーザー操作を遅延させない
- BLE 通信は MVP のスコープ外である

### 将来フェーズ: 5 タスク構成

モバイル連携フェーズでは、以下の 5 タスク構成とコマンドキューによる直列化へ発展する:

| タスク | 責務 |
|---|---|
| UI Task | 画面描画、外周スライド入力、振動 |
| Match Engine Task | 唯一の状態変更主体。ドメインロジックの実行 |
| Event Store Task | LittleFS へのイベント追記、CRC 検証、NVS スナップショット |
| BLE Task | GATT サーバー、接続管理、イベント送受信、分割転送 |
| Power / RTC Task | バッテリー管理、時刻同期、スリープ制御 |

タスク間はコマンドキューで通信し、状態変更は Match Engine Task に集約する:

```
Touch/BLE → DomainCommand Queue → MatchEngine → EventStore → State更新 → UI/BLE通知
```

詳細は [モバイル連携設計](./10-mobile-integration.md) を参照。

## 設定定数の集約

実機テストで決まる閾値やパラメータは `config/app_config.hpp` に集約する。ソースコード中に散在させない。

対象の例（**太字**は Phase 0 実測で根拠が得られた値、それ以外は未検証の設計初期値）:

- **画面中心座標（234, 234）** -- `M5.Display.width()` / `M5.Display.height()` の実測値（Step 2）
- **外周リング下限（165px）** -- 実測 p0（最小タッチ半径）に基づく。上限なし（撤廃）（Step 3）
- キャンセル半径（145px） -- 設計値据え置き（未検証）
- **角速度しきい値（0.7 度/ms = 700 度/秒）** -- 実測角速度の約 3 倍。ただし値自体は未検証の初期値（Step 3）
- **振動強度（255 固定）** -- 32〜192 は体感できず、255 のみ体感可能（Step 5）
- **最小体感振動時間（20 ms）** -- 強度 255 で確実に体感できる下限（Step 5）
- 感度角（10 度 / 1 ライフ） -- 未検証。間引き方式次第で変更の可能性あり
- 最低移動角（6 度） -- 未検証
- 無操作タイムアウト（90 秒で減光）
- 各振動パターンの持続時間 -- 提案値あり（[UI/UX 設計](./05-ui-ux.md) 参照）、通しの体感評価は未実施
- NVS スロット数（16）
- 履歴リングバッファサイズ（64）

これらの値は `app_config.hpp` に集約することで調整作業を局所化する。実測で確定した値と未検証の設計初期値を区別し、後者は実機テスト後に調整する前提である。
