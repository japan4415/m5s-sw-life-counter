## 実機が要る作業 / 要らない作業の切り分け

開発を円滑に進めるための最大の要因は、実機が必要な作業とホスト PC で完結する作業を明確に分離することである。

### 実機が必要な作業

| 作業 | 理由 |
|------|------|
| 描画性能の測定 | 468x468 AMOLED への実際の転送速度は実機でしか計測できない |
| タッチ座標系と `atan2()` の符号確認 | 画面座標系によって時計回り・反時計回りの符号が逆転する可能性がある |
| 外周リング半径・感度の実測調整 | 指の太さ・タッチ精度はデバイス固有である |
| 振動の体感確認 | 振動モーターの強度と時間の感覚は数値では判断できない |
| バッテリー実測 | 連続稼働時間は実測必須（450mAh、目標: 4-8 時間） |
| BLE 同時動作確認 | BLE + 画面描画 + タッチの同時動作は実機で検証が必要 |

### 実機不要（ホスト PC で完結する作業）

| 作業 | ホストでの検証方法 |
|------|-------------------|
| ドメインロジック（`LifeService` の 0 クランプ・Undo・履歴管理） | `pio test -e native` |
| 永続化レコードの CRC / シリアライズ | `pio test -e native` |
| ジェスチャー角度計算の純関数部分（`normalizeDelta` 等） | `pio test -e native` |
| 状態遷移ロジック | `pio test -e native` |

### ハードウェア依存の隔離方針

ハードウェアに依存する処理を薄いインターフェース（抽象クラスまたは関数ポインタ）で隔離し、ドメインロジックを実機から切り離す設計とする。これにより `pio test -e native` でホスト上のユニットテストが可能になる。

```
ドメインロジック（純粋な計算） ← テスト対象
       ↓ インターフェース
ハードウェア依存の実装（M5Unified / M5GFX）
```

具体的には、描画・タッチ取得・振動・ストレージ等のハードウェア操作を抽象化し、テスト時にはモック実装に差し替える。

## 基本の開発ループ

実機を USB で接続した状態での開発サイクルは以下のとおりである。

### Step 1: コードを編集する

エディタ（VS Code + PlatformIO IDE 等）でソースコードを編集する。

### Step 2: ビルドする

```bash
pio run
```

コンパイルエラーがないことを確認する。

### Step 3: ファームウェアを書き込む

```bash
pio run -t upload
```

ポートを明示的に指定する場合:

```bash
pio run -t upload --upload-port /dev/cu.usbmodem14301
```

> **注記**: `/dev/cu.usbmodem14301` は例であり、実際のポート名は `ls /dev/cu.usbmodem*` で確認すること。

> **注意**: Native USB-CDC ではチップのリセット時に USB が再列挙されるため、`pio run -t upload` 末尾の `Hard resetting via RTS pin` だけではデバイスが起動しない場合がある。書き込み完了後に**電源ボタンを短押し**してリセットすること。

### Step 4: シリアルモニタでログを確認する

```bash
pio device monitor
```

ポートを指定する場合:

```bash
pio device monitor --port /dev/cu.usbmodem14301
```

> **注意**: `pio device monitor` は TTY を要求するため、非対話環境（CI、SSH 経由のスクリプト等）では `termios.error: (19, 'Operation not supported by device')` で動作しない。その場合は pyserial で直接読む方法を使う（後述の「[pyserial による代替シリアルモニタ](#pyserial-による代替シリアルモニタ)」を参照）。

### Step 5: 書き込み後にデバイスをリセットする

書き込み完了後、デバイスが自動起動しない場合は**電源ボタンを短押し**してリセットする。Native USB-CDC ではチップのリセット時に USB デバイスが再列挙されるため、`Hard resetting via RTS pin` だけでは起動しないことがある。

### Step 6: 動作を確認し、修正があれば Step 1 に戻る

## よく使うコマンド早見表

| 操作 | コマンド |
|------|---------|
| ビルドのみ | `pio run` |
| クリーンビルド | `pio run -t clean && pio run` |
| 書き込み | `pio run -t upload` |
| 書き込み + モニタ | `pio run -t upload -t monitor` |
| モニタのみ | `pio device monitor` |
| モニタ（非対話環境） | `uv run python serial_read.py`（[pyserial 代替](#pyserial-による代替シリアルモニタ)参照） |

| フラッシュ全消去 | `esptool.py --chip esp32s3 --port /dev/cu.usbmodem<実際のポート番号> erase_flash` |

> **注記**: `brew install esptool` でインストールされるコマンド名は環境によって `esptool` または `esptool.py` のいずれかになる。`which esptool esptool.py` で確認すること。

> **注記**: `pio run -t upload -t monitor` はアップロード完了後に自動でシリアルモニタを起動するため、日常的な開発では最も効率的なコマンドである。

## シリアルログの方針

### ボーレート

`platformio.ini` に `monitor_speed = 115200` を設定する。

### ログレベル

`-DCORE_DEBUG_LEVEL` ビルドフラグでログレベルを制御する。

| レベル | 値 | 用途 |
|--------|:---:|------|
| None | 0 | リリースビルド |
| Error | 1 | リリースビルド（エラーのみ） |
| Warn | 2 | 安定版 |
| Info | 3 | 通常開発 |
| Debug | 4 | 開発中のデバッグ |
| Verbose | 5 | 詳細デバッグ（初期開発・問題調査時） |

### ログマクロの使い分け

| マクロ | 用途 |
|--------|------|
| `log_e(tag, ...)` | エラー -- 回復不可能な異常 |
| `log_w(tag, ...)` | 警告 -- 異常だが動作は継続する |
| `log_i(tag, ...)` | 情報 -- 状態遷移や重要なイベント |
| `log_d(tag, ...)` | デバッグ -- 開発中にのみ必要な詳細情報 |

### Native USB-CDC でのログ取りこぼし

Native USB-CDC では、**デバイス起動直後のログが取りこぼされる**ことがある。これは USB-CDC 接続がホスト側で確立される前にデバイスがログを出力してしまうためである。

さらに、Native USB-CDC ではチップのリセット時に USB デバイスが再列挙され、開いていたポートハンドルが無効になる。そのため `setup()` で 1 回だけ出力する診断スケッチは取りこぼしやすい。**診断用スケッチは `loop()` から定期的に出力する作りにすることを推奨する**。

対策:

1. **`pio device monitor` を先に起動しておく** -- デバイスのリセットボタンを押す前にモニタを起動する
2. **起動直後に短い待ちを入れる** -- `setup()` の先頭に `delay(1000)` 等を入れて USB-CDC 接続の確立を待つ（開発中のみ）
3. **診断情報を `loop()` で定期出力する** -- `setup()` のみの 1 回限りの出力ではなく、`loop()` 内で数秒おきに繰り返し出力する設計にする

### リリースビルドでの方針

リリースビルドでは `-DCORE_DEBUG_LEVEL=1`（Error のみ）または `-DCORE_DEBUG_LEVEL=0`（ログ無効）に設定し、バイナリサイズと実行速度への影響を最小化する。

## Phase 0: 実機成立性確認の手順

本プロジェクトの実装は Phase 0（実機成立性確認）から開始する。以下の各ステップを段階的に実施し、各ステップの合格条件を満たしてから次に進む。

### Step 1: 画面表示

**目的**: 基本的な画面描画が動作することを確認する。

> **参考**: [開発環境セットアップの動作確認用最小スケッチ](./02-dev-environment.md#動作確認用の最小スケッチ) をそのまま使用できる。

**手順**:

1. 背景を単色で塗りつぶし、中央にテキストを表示するスケッチを書き込む
2. 468x468 円形 AMOLED の端が欠けないか確認する

**合格条件**:

- 背景色が全画面に表示されている
- テキストが画面中央に表示されている
- 円形ディスプレイの端が欠けず、表示領域全体が使えている

### Step 2: 回転描画

**目的**: 上側プレイヤー用の 180 度回転描画が正しく機能することを確認する。

**手順**:

1. 画面の上半分に 180 度回転したテキストを描画する
2. 画面の下半分に通常方向のテキストを描画する

**合格条件**:

- 上半分のテキストが 180 度回転して表示されている（対面のプレイヤーから正しく読める）
- 下半分のテキストが通常方向で表示されている

#### 実測結果（2026-08-17 実施済み）

全合格条件を満たした。実機の目視で 180 度回転したテキストが正しく表示されることを確認した。

### Step 3: タッチ

**目的**: タッチ座標系を把握し、外周スライド操作の基礎データを取得する。

**手順**:

1. タッチした位置の生の `x`, `y` 座標をシリアルに出力する
2. 中心 (234, 234) からの半径を算出して同時に出力する
3. `atan2(y - 234, x - 234)` の角度を同時に出力する
4. 指で時計回り・反時計回りに外周をなぞり、角度の変化を観察する

**合格条件**:

- タッチ座標が安定して取得できている
- 中心からの半径が妥当な値を示している
- **時計回りで角度が増えるか減るかが確定している** -- この結果を定数として設計に反映する

**参考スニペット（実機未検証）**:

> **注意**: 以下は実機未検証の参考実装である。M5Unified の API 名・引数は実機で `pio run` を通して確認すること。

```cpp
// Phase 0 Step 3: タッチ座標・半径・角度のダンプ（実機未検証）
#include <M5Unified.h>
#include <cmath>

constexpr float kCenterX = 234.0f;
constexpr float kCenterY = 234.0f;

void loop() {
  M5.update();
  auto t = M5.Touch.getDetail();
  if (t.isPressed()) {
    const float dx = t.x - kCenterX;
    const float dy = t.y - kCenterY;
    const float radius = std::sqrt(dx * dx + dy * dy);
    const float degrees = std::atan2(dy, dx) * 180.0f / M_PI;
    Serial.printf("x=%d y=%d r=%.1f deg=%.1f\n", t.x, t.y, radius, degrees);
  }
}
```

**合格条件（追加）**: 画面上で時計回りに指を動かしたとき `deg` が増えるか減るかを記録し、増減の向きを定数として設計に反映すること。

#### 実測結果（2026-08-17 実施済み、826 サンプル）

全合格条件を満たした。

| 指標 | 実測値 |
|---|---|
| サンプリング間隔 中央値 | 15 ms（約 66 Hz） |
| サンプリング間隔 最大 | 270 ms（欠測が起きる） |
| タッチ座標範囲 x | 18 〜 465 |
| タッチ座標範囲 y | 14 〜 466 |
| 中心 (234, 234) からの半径 最小 | 165.0 |
| 中心 (234, 234) からの半径 中央値 | 209.3 |
| 中心 (234, 234) からの半径 最大 | 268.2 |
| 表示円（半径 234）外のサンプル | 826 件中 117 件（14.2%） |
| 時計回りの角度変化 | **増加**（+363.6 度/周） |
| 反時計回りの角度変化 | 減少（-372.3 度/周） |

**判明した設計含意**:

- タッチ有効範囲は表示円（半径 234）より広い。半径の上限で入力を弾くと正当な操作を落とす
- サンプル落ち（最大 270 ms）があるため、ジェスチャー判定は経過時間で正規化した速度で行う必要がある
- `atan2(dy, dx)` は画面座標系（y 下向き）では時計回りで増加する。数学的標準（反時計回りが正）とは逆

### Step 4: ボタン

**目的**: 物理ボタンの入力検出を確認する。

**手順**:

1. `M5.BtnA`（KEYA / GPIO2）の短押し・長押しを検出してシリアルに出力する
2. `M5.BtnB`（KEYB / GPIO1）の短押し・長押しを検出してシリアルに出力する
3. A + B の同時押しを検出してシリアルに出力する

**合格条件**:

- BtnA の短押しが検出できる
- BtnB の短押しが検出できる
- 長押し（500ms 以上）が短押しと区別できる
- 同時押しが検出できる

#### 実測結果（2026-08-17 実施済み）

全合格条件を満たした。

| 指標 | 実測値 |
|---|---|
| BtnA（KEYA / GPIO2）の物理位置 | 画面正面から見て**左** |
| BtnB（KEYB / GPIO1）の物理位置 | 画面正面から見て**右** |
| BtnA 短押し検出 | OK |
| BtnB 短押し検出 | OK |
| 長押し（500ms 以上）の区別 | OK |
| A + B 同時押し検出 | OK |

**判明した設計含意**: 左ボタン = Undo、右ボタン = タッチロック切り替えの配置が確定した。

### Step 5: 振動

**目的**: 振動フィードバックの強度と持続時間の体感を確認する。

**手順**:

`M5.Power.setVibration()` を以下の各パラメータで呼び出し、体感を記録する。

| 持続時間 | 用途（想定） |
|----------|-------------|
| 10ms | スライド中の 1 ライフ通過 |
| 15ms | スライド中の 1 ライフ通過（やや強め） |
| 30ms | スライド操作開始 |
| 40ms | 確定時 |
| 100〜150ms | ライフ 0 到達 |

**合格条件**:

- 各持続時間での振動が区別できる
- 操作用途として適切な強度であるか判断できるデータが得られている

#### 実測結果（2026-08-17 実施済み）

**重要な発見**: `M5.Power.setVibration(uint8_t level)` の引数は**持続時間ではなく強度（0〜255）**である。`setVibration(0)` を書くまでモーターは回り続ける。内部実装は M5IOE1 の `pwm_ch1`（GPIO9）へ 12bit PWM を出力する（`duty12 = level * 0x0FFF / 255`）。

上記の手順表は「持続時間」を変数としていたが、実際には「強度」が変数であり、時間制御は `millis()` 等で呼び出し側が管理する必要がある。

| 指標 | 実測値 |
|---|---|
| 体感できた最低強度 | 255（32〜192 では体感できず） |
| 強度 255 での最低体感持続時間 | 15 ms（かろうじて）、20 ms（確実） |

**判明した設計含意**:

- 振動の強弱を設計変数にできない（255 でしか体感できない）。フィードバックの種類は時間の長短でのみ区別する
- 1 ライフ通過の振動（設計値 10〜15 ms）は体感困難。20 ms 以上を推奨
- 操作開始（30 ms）、確定（40 ms）、ライフ 0（100〜150 ms）は設計値どおり十分に体感可能

### Step 6: バッテリー

**目的**: バッテリー残量の取得と USB 給電判定を確認する。

**手順**:

1. バッテリー残量をパーセンテージで取得し、シリアルに出力する
2. USB 給電中か否かを判定し、シリアルに出力する

**合格条件**:

- バッテリー残量が取得できている（0-100% の範囲）
- USB 給電中 / バッテリー駆動中が正しく判定できている

#### 実測結果（2026-08-17 実施済み）

合格条件を**部分的に**満たした。バッテリー残量は取得できるが、USB 給電判定は `isCharging()` では不十分である。

| API | 実測値 | 備考 |
|---|---|---|
| `M5.Power.getBatteryLevel()` | 100（USB 接続・満充電時） | 0〜100% で正常取得 |
| `M5.Power.getBatteryVoltage()` | mV 単位で正常取得 | |
| `M5.Power.isCharging()` | 0（false）（USB 接続・満充電時） | 満充電で充電停止するため false |
| `M5.Power.getBatteryCurrent()` | -- | **使用不可**（HW 制限。公式記載） |

**判明した設計含意**:

- `isCharging()` を「USB 給電中かどうか」の判定に使うのは不適当。満充電時は充電が止まるため false になる
- USB 給電判定の代替手段は未解決。今後の課題として残す
- バッテリー電流は読み取れないため、消費電力の実測は外部計測器が必要

### Step 7: PSRAM

**目的**: 全画面バッファの PSRAM 上への確保が可能か確認する。

**手順**:

1. 468 x 468 x 2 byte = 438,048 bytes ≈ 427.8 KiB の `M5Canvas` を PSRAM 上に確保する
2. 確保の成否を判定し、シリアルに出力する
3. 確保に失敗した場合のエラーハンドリングが機能するか確認する

**合格条件**:

- `M5Canvas` が PSRAM 上に確保できている
- 確保失敗時のエラーが検出・ログ出力できている
- PSRAM の空き容量が確認できている

#### 実測結果（2026-08-17 実施済み）

全合格条件を満たした。

| 指標 | 実測値 |
|---|---|
| Canvas 確保 | 成功（468x468 16bit、PSRAM 上） |
| 消費メモリ | 438,068 bytes（期待値 438,048 bytes とほぼ一致） |
| 確保後の PSRAM 空き | 7,509,919 bytes |

PSRAM 空き容量は十分であり、将来のイベントログバッファやフォントデータにも余裕がある。

### Step 8: 描画レート

**目的**: 全画面バッファの転送性能を計測し、描画方式を決定する。

**手順**:

1. 全画面 Canvas に描画して画面に転送する処理を繰り返す
2. 1 回の転送にかかる時間を `millis()` で計測し、シリアルに出力する
3. 複数回の平均値を算出する

**合格条件**:

- 転送 1 回あたりの所要時間が計測できている
- 方式 1（全画面一括転送）で実用的なフレームレート（目安: 30fps 以上 = 33ms 以下）が得られるか判断できている
- 方式 1 で不足する場合、方式 2（上下分割）または方式 3（部分再描画）の検討データが得られている

#### 実測結果（2026-08-17 実施済み）

合格条件を満たした。全画面一括転送は 30 FPS 目標に未達だが、部分再描画で十分なフレームレートが得られることを確認した。

| 方式 | 転送時間（中央値） | FPS |
|---|---|---|
| 全画面 468x468 | 44,639 us | 22.4 |
| 上半分 468x234 | 22,312 us | 44.8 |
| 中央 200x120 | 4,994 us | 200.2 |

**判明した設計含意**:

- 全画面一括転送（22.4 FPS）は 30 FPS 目標を下回る。UI は部分再描画を前提に組む必要がある
- 上半分転送（44.8 FPS）は 30 FPS を超えており、プレイヤーエリア単位の更新は実用的
- 中央部の小領域（200x120）は 200 FPS と高速。数値表示の更新は十分高速

### Phase 0 の残項目

Step 1 〜 Step 8 はすべて実施済みである（Step 1 は開発環境セットアップ時に確認済み）。Phase 0 の未実施項目は **BLE の同時動作確認**（BLE + 画面描画 + タッチの同時動作検証）のみであり、これは将来の BLE 連携フェーズ（Phase 5 以降）の前提条件として実施する。

### 計測の実務ノウハウ

Phase 0 の実機計測で得られた知見を以下に記録する。

#### シリアル出力フォーマット

計測用スケッチは**機械解析しやすい固定フォーマット**で 1 行 1 サンプル出力すると、後段の解析が容易になる。

推奨フォーマット例:

```
T,<millis>,<x>,<y>,<radius>,<deg>
```

- 各フィールドをカンマ区切りにし、ヘッダ行は `#` で始めるとフィルタしやすい
- 指を離した区切りは `T,END` のようなマーカーを出力すると、ジェスチャー単位で切り分けられる

#### 画面ガイドの表示

画面に `TOP` / `R` / `BOTTOM` / `L` のガイドラベルを描いておくと、操作者と座標系の向きを確実に合わせられる。特に丸型画面では上下の判別が曖昧になりやすいため有効である。

#### 角度の累積計算

`atan2()` は +/-180 度の範囲で値を返すため、境界またぎ（例: +179 度 → -179 度）を畳んでから累積する必要がある。畳まずに差分を取ると一周ごとに +/-360 度のジャンプが発生し、回転量の集計が破綻する。

```cpp
// 境界またぎの正規化例
float delta = current_deg - prev_deg;
if (delta > 180.0f) delta -= 360.0f;
if (delta < -180.0f) delta += 360.0f;
cumulative += delta;
```

#### `setVibration()` の引数は強度であり時間ではない

`M5.Power.setVibration(uint8_t level)` の引数は**持続時間ではなく強度（0〜255）**である。この取り違えにより「振動が動作しない」と誤診した実例がある。

- `setVibration(40)` は「40 ms の振動」ではなく「強度 40 の振動を開始」する意味であり、32〜192 の範囲では体感できないため「壊れている」と誤認しやすい
- 振動を止めるには `setVibration(0)` を明示的に呼ぶ必要がある。呼ばなければモーターは回り続ける
- 時間で振動を表現するには、`setVibration(255)` → `millis()` で経過を監視 → `setVibration(0)` の手順が必要

#### `-DCORE_DEBUG_LEVEL=5` の I2C ログ

`-DCORE_DEBUG_LEVEL=5`（Verbose）を設定すると、起動時に `[LGFX] i2c write error : ack wait` が大量に出力される。動作に支障は無いが、**計測値を含むシリアルログが埋もれる**。

対処法:

- シリアル出力を `grep` で絞って計測値だけを抽出する（例: `grep '^T,' serial_output.txt`）
- 計測が終わったら `-DCORE_DEBUG_LEVEL=3`（Info）以下に戻す
- 常用時は Verbose を使わない想定とする

## pyserial による代替シリアルモニタ

`pio device monitor` は TTY を要求するため、非対話環境（CI、SSH 経由のスクリプト、Claude Code 等）では動作しない（`termios.error: (19, 'Operation not supported by device')` が発生する）。この場合、pyserial で直接ポートを読む方法を使う。

```python
# serial_read.py -- pyserial による簡易シリアルモニタ
import serial

port = "/dev/cu.usbmodem14301"  # 実際のポート名に置き換え
ser = serial.Serial(port, 115200, timeout=1)
ser.setDTR(True)  # macOS の /dev/cu.* は DTR を上げないため明示的に設定
try:
    while True:
        line = ser.readline()
        if line:
            print(line.decode("utf-8", errors="replace"), end="")
except KeyboardInterrupt:
    pass
finally:
    ser.close()
```

> **注記**: macOS の `/dev/cu.*` デバイスは DTR（Data Terminal Ready）を自動で上げない。pyserial で読むときは `ser.setDTR(True)` を明示するとデバイスとの通信が安定する。

> **注記**: Native USB-CDC ではチップのリセット時に USB デバイスが再列挙され、ポートハンドルが無効になる。そのため書き込み後にこのスクリプトを起動し直す必要がある場合がある。

## トラブルシューティング

| 症状 | 原因 | 対処 |
|------|------|------|
| `ls /dev/cu.*` にデバイスが出ない | 充電専用ケーブルを使用している | データ通信対応の USB-C ケーブルに交換する |
| 同上 | USB ハブ経由で接続している | Mac 本体の USB-C ポートに直接接続する |
| 同上 | ダウンロードモードに入っていない | 電源ボタン約 2 秒長押し（緑 LED 点灯で離す）を試す |
| アップロード後にポート名が変わる | Native USB-CDC の仕様である。ファームウェアが変わると USB デバイスが再列挙され、ポート番号が変化する | 再度 `ls /dev/cu.usbmodem*` でポート名を確認する |
| `A fatal error occurred: Failed to connect` | デバイスがダウンロードモードになっていない | 手動でダウンロードモード（電源ボタン 2 秒長押し → 緑 LED）に入ってから再試行する |
| 書き込み後にブートループする | ファームウェアの不具合、またはフラッシュの破損 | Boot ボタン（GPIO0）を押しながら USB ケーブルを抜き差しして強制ブートローダーモードに入り、`esptool.py --chip esp32s3 --port /dev/cu.usbmodem<実際のポート番号> erase_flash` でフラッシュを全消去してから書き込み直す。文鎮化時はポートの自動検出が失敗しやすいため、`--port` の明示指定が必須である |
| 画面が真っ黒 | `board_build.arduino.memory_type` が正しくない | `platformio.ini` で `board_build.arduino.memory_type = qio_opi` を設定する |
| 同上 | PSRAM の設定不足 | `-DBOARD_HAS_PSRAM` ビルドフラグを追加する |
| 同上 | M5Unified のバージョンが古い | M5Unified を 0.2.15 以上に更新する |
| シリアルに何も出ない | `-DARDUINO_USB_CDC_ON_BOOT=1` が欠落している | `platformio.ini` の `build_flags` に `-DARDUINO_USB_CDC_ON_BOOT=1` と `-DARDUINO_USB_MODE=1` の両方を追加する |
| 同上 | モニタの起動タイミングが遅い | `pio device monitor` を先に起動してからデバイスをリセットする。または `setup()` 先頭に `delay(1000)` を追加する |
| タッチ座標が飛ぶ | ノイズまたは指の浮き | サンプル間で 30 度以上のジャンプが発生した場合、そのサンプルを無視するフィルタを実装する |
| PSRAM 確保失敗 | `-DBOARD_HAS_PSRAM` が欠落している | `build_flags` に `-DBOARD_HAS_PSRAM` を追加する |
| 同上 | `memory_type` が正しくない | `board_build.arduino.memory_type = qio_opi` を設定する |
| 書き込み後にデバイスが起動しない | Native USB-CDC の `Hard resetting via RTS pin` だけでは起動しない場合がある | **電源ボタンを短押し**してリセットする。公式のファクトリーリストア手順にも「書き込み完了後にリセットボタンを押す」と明記されている |
| `pio device monitor` で `termios.error` が出る | TTY が必要だが非対話環境で実行している | pyserial で直接読む（上記「[pyserial による代替シリアルモニタ](#pyserial-による代替シリアルモニタ)」を参照） |

## git / ブランチ運用

### ブランチ戦略

- **機能単位でブランチを作成する** -- `feature/phase0-display`, `feature/phase0-touch` のように Phase 0 の各ステップでもブランチを分けてよい
- `main` ブランチには動作確認済みのコードのみをマージする

### コミットの方針

- **実機で検証済みのファームウェア設定は、必ずコミットに含める** -- 動作する `platformio.ini` が常にリポジトリに存在する状態を保つ
- `platformio.ini` のバージョン変更（`platform`, `lib_deps` の更新）は**単独のコミット**にする -- 他のコード変更と混ぜない
- Phase 0 の計測値が確定したら、`config/app_config.hpp` の定数更新と計測記録を同じコミットに含める

## 安全上の注意

### バッテリーに関する注意

M5Stack StopWatch は **450mAh のリチウムバッテリーを内蔵**している。以下の点に注意すること。

- **長時間の高輝度連続通電を避ける** -- 開発中は適宜休憩を入れ、不要な場合は画面輝度を下げる
- バッテリー残量が著しく低下した状態での長時間の書き込み試行は避ける

### `BAT` ラベルの誤記について

> **重要**: 公式ドキュメントにおいて、`BAT` と表記されたピンは**実際には `5V IN`（外部電源入力用）**であり、バッテリー直結ではない。外部給電時にこのピンを使用する場合は、**誤配線に十分注意すること**。バッテリーに直接電圧を印加するとデバイスが破損する可能性がある。
