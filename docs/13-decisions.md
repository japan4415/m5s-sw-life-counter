## ADR-01: 操作方式 — 外周スライド方式を採用し、タップ方式を却下

### 文脈

円形 AMOLED タッチディスプレイ（466x466px）を持つ M5Stack StopWatch で、2 人のプレイヤーのライフを変更する操作方式を決定する必要があった。初期設計ではタップ方式（画面上の +/- ボタン）を採用していたが、ユーザーから「縁をスライドする操作はどうか / 開始地点によってどちらのライフを変動させるか変える」という提案があり、比較検討を行った。

### 決定

外周スライド方式を採用し、タップ方式を廃止する。

### 比較表

| 項目 | タップ | 外周スライド |
|------|-------|------------|
| ±1の速さ | 高い | やや遅い |
| ±5以上の入力 | 連打が必要 | 1操作で可能 |
| 誤接触への強さ | 弱い | 強い |
| 操作の分かりやすさ | 高い | 説明表示が必要 |
| 物理的な楽しさ | 普通 | 高い |
| 円形画面との相性 | 普通 | 非常によい |
| Undo履歴 | 連打ごとになりやすい | 1スライドを1件にできる |
| 対象プレイヤーの判別 | ボタン位置次第 | 開始地点で明確 |
| 画面中央の視認性 | ±ボタンで狭くなる | ライフ表示を大きくできる |

### 根拠

- 円形画面との相性が非常によく、デバイスの特徴を活かせる
- 誤接触に強く、大会環境での信頼性が高い
- 1 スライドを 1 件として履歴管理でき、Undo が直感的になる
- 画面中央をライフ表示専用にでき、視認性が向上する
- ±5 以上の大きな変動を 1 操作で入力できる

### 影響／トレードオフ

- 操作の分かりやすさが下がるため、初回利用時に説明表示が必要である
- ±1 の入力が僅かに遅い（最低 10 度のスライドが必要）
- タッチ感度・閾値の実機調整が必須である

## ADR-02: UI ライブラリ — LVGL を使わず M5GFX で直接描画

### 文脈

466x466px の円形 AMOLED に描画する方法として、LVGL（組込み向け GUI ライブラリ）と M5GFX（M5Stack 公式グラフィックスライブラリ）を比較した。

### 決定

LVGL を使わず、M5GFX で直接描画する。

### 根拠

本アプリケーションの UI 規模は小さく、画面数も限られている（ゲーム画面、セットアップ画面、メニュー画面、履歴画面）。LVGL のウィジェットシステム・テーマエンジン・イベントモデルは過剰であり、学習コストと依存の複雑さに見合わない。M5GFX は M5Unified と統合されており、`M5Canvas`（PSRAM 上のオフスクリーンバッファ）を使った全画面描画が可能である。

### 影響／トレードオフ

- レイアウト管理やアニメーションを自前で実装する必要がある
- UI が複雑化した場合にスケーラビリティが低い
- M5Stack エコシステムとの親和性は高い

## ADR-03: フレームワーク — MVP は Arduino Framework + M5Unified / M5GFX

### 文脈

ESP32-S3 の開発フレームワークとして Arduino Framework と ESP-IDF を比較した。

### 決定

MVP は Arduino Framework + M5Unified + M5GFX で開発する。将来的に省電力制御やモバイル連携で ESP-IDF への移行がありうる。

### 根拠

M5Unified が Arduino Framework 上でディスプレイ・タッチ・ボタン・振動・電源・バッテリーを統一的に扱える。M5Unified は M5StopWatch を対応デバイスとして掲載している。また、公式に ESP-IDF ベースの StopWatch デモ（`M5StopWatch-UserDemo`）が存在するため、移行パスも確保されている。

### 影響／トレードオフ

- Arduino Framework は ESP-IDF の上に構築されているため、低レベルの制御が必要になった場合に制約がある
- ESP-IDF への移行は大きな作業だが、ドメインロジック層はフレームワーク非依存に設計しておくことで影響を最小化できる

## ADR-04: 永続化 — NVS 16 スロットローテーション

### 文脈

ESP32 の NVS（Non-Volatile Storage）は Flash ベースであり、同一キーへの頻繁な更新は Flash セクタの摩耗を招く。ライフカウンターでは操作ごとに状態を保存する必要がある。

### 決定

NVS に 16 個のスロット（`state_00` 〜 `state_15`）を設け、ローテーションで書き込む。イベントログは LittleFS へ分離する。

### 根拠

- 同一キーの更新継続による NVS 劣化を避けるため、複数スロットをローテーションする
- NVS は頻繁な大容量ログの保存に不向きであるため、イベントログは LittleFS に分離する
- 16 スロットあれば、書き込み途中の電源断でも健全なスロットから復元できる

### 影響／トレードオフ

- スロット管理（sequence 番号の追跡、最新スロットの特定）のロジックが必要になる
- NVS の容量を 16 スロット分消費する
- LittleFS の電源断耐性は別途テストが必要である（要実機確認）

## ADR-05: 通信 — M5Stack から直接クラウドへ接続しない

### 文脈

試合記録をクラウドにバックアップする方法として、M5Stack から直接 HTTPS でクラウド API に接続する方式と、スマホを中継する方式を比較した。

### 決定

M5Stack から直接クラウドへ接続せず、スマホを中継する。

### 根拠

- Tournament Mode の要件として、M5Stack の Wi-Fi を初期化しないことが求められている
- ファームウェアに認証情報・TLS 証明書・Wi-Fi 設定を持ち込みたくない
- M5Stack 単独で全機能が動作することを必須要件としているため、クラウド接続は任意であるべきである

### 影響／トレードオフ

- クラウドへのバックアップにはスマホが必要になる
- スマホが手元にない場合、試合記録は M5Stack のローカルストレージにのみ保存される

## ADR-06: BLE スタック — ESP-NimBLE

### 文脈

ESP32-S3 で BLE を使用する場合、Bluedroid と NimBLE の 2 つのスタックが選択肢となる。

### 決定

ESP-NimBLE を採用する。

### 根拠

NimBLE は Bluedroid と比較してコードサイズとメモリ負荷が小さい。M5Stack StopWatch は PSRAM 8MB を搭載しているが、画面バッファ（約 424 KiB）と他の処理で内部 SRAM を消費するため、BLE スタックのメモリフットプリントは小さい方が望ましい。

### 影響／トレードオフ

- NimBLE は Classic Bluetooth をサポートしない（BLE のみ）。本プロジェクトでは Classic Bluetooth を使用しないため問題ない
- BLE が M5Stack StopWatch の基板上で動作するかは要実機確認である

## ADR-07: シリアライズ — CBOR

### 文脈

BLE 経由でイベントデータをスマホに送信する際のシリアライズ形式を選択する必要があった。

### 決定

CBOR（Concise Binary Object Representation）を採用する。

### 根拠

BLE の MTU は通常 23〜512 bytes であり、データサイズの最小化が重要である。CBOR は JSON と同等の表現力を持ちながらバイナリ形式のためサイズが小さい。

### 影響／トレードオフ

- 人間が直接読めないため、デバッグ時には CBOR → JSON 変換ツールが必要になる
- CBOR のエンコーダ／デコーダライブラリが必要になる（ファームウェア側とスマホ側の双方）

## ADR-08: スマホアプリ — Kotlin Multiplatform

### 文脈

Android と iPhone の両方に対応するスマホアプリの開発方式を選択する必要があった。

### 決定

Kotlin Multiplatform でビジネスロジックを共有し、UI と BLE はネイティブで実装する。Android は Kotlin + Jetpack Compose、iPhone は SwiftUI + CoreBluetooth を使用する。

### 根拠

- ビジネスロジック（イベントモデル、CBOR コーデック、状態復元 Reducer、同期ステートマシン）を 1 箇所で実装・テストできる
- BLE のバックグラウンド処理はプラットフォーム固有の API（Android: `CompanionDeviceManager`、iOS: CoreBluetooth の State Preservation and Restoration）に依存するため、ネイティブ実装が必要である
- UI もプラットフォーム標準に合わせることで、ユーザー体験を損なわない

### 影響／トレードオフ

- 2 つのネイティブ UI を開発・メンテナンスする必要がある
- KMP のビルド環境の構築が必要になる

## ADR-09: 並行性 — MVP は単一の非ブロッキングループ

### 文脈

ファームウェアの並行処理モデルとして、FreeRTOS マルチタスクと単一のイベントループを比較した。

### 決定

MVP は `loop()` 関数による単一の非ブロッキングイベントループで実装する。`delay()` は使用せず、`millis()` または ESP-IDF の単調増加タイマーで時間管理する。

### 根拠

MVP の範囲（ライフ表示・タッチ入力・振動・永続化）では、複雑なマルチタスクは不要である。単一ループの方がデバッグが容易で、競合状態やデッドロックのリスクがない。

### 影響／トレードオフ

- BLE 連携フェーズでは処理の複雑さが増し、マルチタスク（UI Task / Match Engine Task / Event Store Task / BLE Task / Power Task）への移行が必要になる可能性がある
- 単一ループでは長時間ブロックする処理を入れられない

## ADR-10: クラウドは任意

### 文脈

試合記録のバックアップ・共有・統計をクラウドで提供するかを決定する必要があった。

### 決定

クラウドは任意とし、M5Stack 単独で全機能が動作することを必須要件とする。

### 根拠

- 大会環境ではインターネット接続が保証されない
- Tournament Mode では外部通信を行わないことが要件である
- クラウドが停止・廃止されてもデバイス単独で使い続けられることが望ましい

### 影響／トレードオフ

- クラウド同期なしでは、複数端末間でのデータ共有ができない
- 試合共有リンクの生成にはクラウドが必要である

## ADR-11: 既定モードを Tournament Mode とする

### 文脈

通常モード（Casual Mode）と Tournament Mode のどちらをデフォルトにするかを決定する必要があった。

### 決定

既定モードを Tournament Mode とする。

### 根拠

Tournament Mode は通信機能を無効にし、公平性を担保する。大会で使用する際に設定変更を忘れるリスクを排除するため、より制限の強いモードをデフォルトにする。

### 影響／トレードオフ

- カジュアルに使いたいユーザーが Tournament Mode の制約を知らずに困る可能性がある（スマホ連携が使えない等）
- 試合開始後はモード切り替え不可のため、開始時に選択を誤ると試合をやり直す必要がある

| M5GFX | 0.2.21 |

### 根拠

M5Stack 公式ドキュメントで M5StopWatch の対応バージョンとして明記されている。

### 影響／トレードオフ

- `platformio.ini` の `lib_deps` でバージョンを厳密に固定することを推奨する

## ADR-13: 外周リングの半径に上限を設けない

- 記録日: 2026-08-17
- 状態: 採用

### 文脈

外周スライド方式の操作リングは当初、半径 170〜225px（表示領域 0〜169px の外側、画面の円形表示領域 半径 234px の内側）として設計していた。Phase 0 Step 3/4 の実機タッチ計測（826 サンプル）で、外周を一周なぞるジェスチャーのタッチ座標分布を確認した。

### 決定

外周リングの判定を「半径 165px 以上」とし、上限を設けない。表示領域は 0〜164px、キャンセル半径 145px は据え置きとする。

### 根拠

- 826 サンプル中、半径 170〜226px に収まったのは 608 件（73.6%）のみ。外側へのはみ出しが 205 件（24.8%）あり、上限を設けると正当な操作の約 4 分の 1 を棄却してしまう
- タッチ IC（CST820B）は表示円（半径 234px）より外側の座標も返す（117 サンプルが該当）。実測タッチ半径の最大値は 268.2 であった
- 座標範囲は x 18〜465、y 14〜466 であり、物理的なタッチ可能領域は表示領域より広い

### 影響／トレードオフ

- 画面外縁より外側の誤接触（端を持った際の意図しないタッチなど）もリング入力として扱われる。ただし、キャンセル半径（145px）への引き込みと、開始禁止領域（左右各 20 度）で一定の誤操作防止は維持される
- 内側の閾値を 170px から 165px に引き下げたことで、表示領域との隙間が 1px に縮小し、表示領域へのタッチがリング操作として誤検出される可能性がわずかに増加する

## ADR-14: ジャンプ除外を絶対角度から角速度判定に変更

- 記録日: 2026-08-17
- 状態: 採用

### 文脈

外周スライド方式では、タッチ座標のノイズや指の跳ねによる不正な角度変化を除外する必要がある。当初の設計では「1 サンプルあたり 30 度以上のジャンプを無視する」という絶対角度方式を採用していた。Phase 0 Step 3/4 の実機タッチ計測で、サンプリング間隔の実態を確認した。

### 決定

ジャンプ除外の判定を絶対角度方式から角速度方式に変更する。`abs(deltaDeg) / deltaMs` を計算し、しきい値を超えた場合にそのサンプルを無視する。しきい値の初期提案値は 0.7 度/ms（700 度/秒）とする。

### 根拠

- タッチのサンプリング間隔は中央値 15 ms（約 66 Hz）だが、最大 270 ms の欠測が発生する
- 実測の角速度は約 233 度/秒であり、270 ms の欠測後に約 63 度の正当な角度変化が生じうる。絶対角度方式（30 度/サンプル）ではこれを誤って棄却してしまう
- 角速度方式であれば、欠測時間を考慮した判定が可能であり、正当な操作を棄却するリスクが低い

### 影響／トレードオフ

- しきい値（0.7 度/ms）は初期提案値であり、実機での調整が必要である。この値自体は未検証
- 時間解像度（`millis()` の精度）に依存するため、極端に短い間隔（1 ms 以下）では判定が不安定になる可能性がある
- 絶対角度方式と比較して計算量がわずかに増加する（除算が追加される）

## ADR-15: MVP の描画方式を全画面転送から部分再描画に変更

- 記録日: 2026-08-17
- 状態: 採用

### 文脈

MVP の描画方式は当初、PSRAM 上の全画面 Canvas（468x468x16bit）を毎フレーム AMOLED に転送する全画面転送方式を想定していた。Phase 0 Step 8 の実機計測で描画レートを実測したところ、全画面転送の中央値は 44,639 us（22.4 FPS）であった。一方、外周スライド操作中のライフ表示更新間隔は約 43 ms である（実測スイープ角速度 233 度/秒、感度 10 度/ライフから算出）。全画面転送 44.6 ms ではこの更新間隔を超過し、ライフ変更のたびに描画が間に合わなくなる。

### 決定

MVP の描画方式を全画面転送から部分再描画に変更する。変更が生じた領域のみを Canvas に描画し、部分的に転送する。

### 根拠

- 全画面転送（468x468）の所要時間 44,639 us に対し、ライフ表示の更新間隔が約 43 ms であり、描画予算を超過する
- 上半分（468x234）の転送は 22,312 us（44.8 FPS）、中央 200x120 の転送は 4,994 us（200.2 FPS）であり、部分再描画であれば十分な描画予算が確保できる
- 外周スライド操作中に変化するのはライフ数値とプレビュー表示のみであり、背景や外周リングの再描画は不要である

### 影響／トレードオフ

- 差分管理（dirty region tracking）の実装が必要になり、描画ロジックの複雑さが増す
- 画面全体のレイアウト変更（画面遷移など）では引き続き全画面転送が必要であり、2 つの描画パスを持つことになる
- 部分再描画の描画予算が 43 ms 以内に収まり続けることを回帰テストで確認する必要がある（L2 テスト項目として追加）

## ADR-16: 振動の強度を 255 固定とし、強弱は時間の長短で表現

- 記録日: 2026-08-17
- 状態: 採用

### 文脈

設計書では振動の強弱を `M5.Power.setVibration()` の引数（0〜255）で制御し、ライフ通過時の軽い触覚フィードバック（弱い振動）とライフ 0 到達時の警告（強い振動）を使い分ける想定であった。Phase 0 Step 5 の実機計測で振動の体感を確認したところ、この想定が実測で否定された。

`M5.Power.setVibration(uint8_t)` の引数は強度（0〜255）であり、`setVibration(0)` を書くまで振動は止まらない。実装は M5IOE1 の `pwm_ch1`（GPIO9）への 12bit PWM である。

### 決定

振動の強度を 255 固定とし、振動の強弱の表現は時間の長短で行う。

### 根拠

- 実測で強度 32〜192 は体感できず、255 でのみ体感できた
- 強度 255 において、15 ms はかろうじて体感でき、20 ms で確実に体感できた
- 強度による段階的な振動表現が物理的に成立しないため、時間の長短で代替する

### 影響／トレードオフ

- 設計書が想定していた「弱い警告振動」（ライフ通過時の軽いフィードバック）のような強度段階の表現力が失われる
- 振動のオン・オフ（255 と 0 の切り替え）をタイマーで管理する実装が必要になる
- 指定時間経過後に `setVibration(0)` を確実に呼ぶ仕組みが必要であり、呼び忘れると振動が止まらなくなる

## ADR-17: 振動の間引きを必須要件に格上げ

- 記録日: 2026-08-17
- 状態: 採用

### 文脈

設計書では振動の間引きを「MVP 後に検討する任意の改善項目」として位置付けていた。Phase 0 Step 5/8 の実測結果により、この前提が崩れた。

外周スライド操作中のライフ表示更新間隔は約 43 ms（スイープ角速度 233 度/秒、感度 10 度/ライフ）である。ADR-16 により振動の最低体感時間は 20 ms と確定した。43 ms 間隔に 20 ms パルスを入れるとデューティ比は約 47% となり、ライフ 1 段階ごとのクリック感ではなく連続振動と体感される。

### 決定

振動の間引きを必須要件に格上げする。ただし、間引きの具体的な方式は未決定であり、以下の 2 つの候補がある:

1. **間引き方式**: ライフ段階ごとの振動パルスを N 段階に 1 回に間引く（例: 3 段階に 1 回のみ振動）
2. **感度見直し方式**: 感度を 10 度/ライフから引き下げてライフ更新間隔を広げ、パルス間の無音区間を確保する

どちらを採用するか、または両者の組み合わせとするかは Phase 1 の実機テストで決定する。

### 根拠

- 43 ms 間隔に 20 ms パルスでデューティ比約 47% は連続振動であり、ライフ変動のクリック感（触覚フィードバック）として機能しない
- 間引きなしでは 10 ライフ以上の変動で不快な連続振動になることが予測される
- この問題は「MVP 後の改善」ではなく、触覚フィードバックの設計が根本的に成立しないため、MVP 段階での対応が必要である

### 影響／トレードオフ

- 間引き方式を採る場合、間引きロジック（パルスカウンタとスキップ判定）の実装が必要になる
- 感度見直し方式を採る場合、一周で変更できるライフ数が減少し、大きなライフ変動に複数周回が必要になる
- いずれの方式でも、ライフ 0 到達時の警告振動（長い振動パルス）は間引きの対象外とし、確実に体感させる必要がある
- 具体的な方式の選定が Phase 1 のブロッカーとなる可能性がある

## Phase 0 実地知見

Phase 0 の作業中に判明した実務上の知見を記録する。記録日: 2026-08-17。

1. **`uv tool install platformio` は `--with pip` が必須。** PlatformIO が内部で `python -m pip` を呼ぶため、pip の無い uv ツール環境では `MissingPackageManifestError` で失敗する。

2. **`pio device monitor` は TTY を要求するため非対話環境では動かない**（`termios.error: (19, 'Operation not supported by device')`）。シリアル出力の確認には pyserial で直接ポートを開いて読む必要がある。

3. **Native USB-CDC ではチップのリセットで USB が再列挙され、開いていたポートハンドルが無効になる。** `setup()` で 1 回だけ出力する診断スケッチは取りこぼしやすいため、`loop()` から定期出力する作りが確実。

4. **ダウンロードモード中はアプリが動かない。** 長押しでダウンロードモードに入れたままだとシリアルは完全に無音になり、「アプリのクラッシュ」と区別がつかない。切り分け時はまず電源ボタン短押しで通常起動させること。

5. **`/dev/cu.usbmodem*` は ESP32-S3 の ROM が常時提供する USB Serial/JTAG であり、ポートの存在はアプリが動いている証拠にならない。**

6. **M5GFX は StopWatch を I2C プローブで自動判別する**（GPIO47=SDA / GPIO48=SCL、RX8130 0x32・BMI270 0x68・CST820 0x15 の存在で判定）。ビルド時マクロによるボード固定は不要。

7. **公式 `platformio.ini` には `M5PM1`（電源管理 IC）と `M5IOE1`（IO エキスパンダ）のライブラリが含まれる。** AMOLED・バイブは M5IOE1 配下の電源レール L3B にぶら下がる。

8. **公式のファクトリーリストア手順に「書き込み完了後、デバイスのリセットボタンを押す」と明記がある。**

9. **計測用スケッチは機械解析しやすい固定フォーマットで出力する。** `T,<millis>,<x>,<y>,<radius>,<deg>` 形式の 1 行 1 サンプル、ジェスチャー間の区切りマーカー、画面上の方位ガイド（N/E/S/W）を含めると、ログの後処理（CSV パース、統計計算）が容易になる。自由形式のテキスト出力は後から解析しづらい。

10. **`setVibration()` の引数は強度（0〜255）であり、時間ではない。** `M5.Power.setVibration(uint8_t)` の引数を時間（ミリ秒）と取り違えると、`setVibration(0)` を呼ぶまで振動が止まらず「振動していない」と誤診する。実装は M5IOE1 の `pwm_ch1`（GPIO9）への 12bit PWM である。API の引数の意味は公式ソースコードで必ず確認すること。

11. **`-DCORE_DEBUG_LEVEL=5` は起動時に I2C ログを大量に出力する。** M5GFX の自動判別が I2C プローブを多数行うため、デバッグレベル最大ではシリアルに大量のログが流れ、計測値の読み取りを妨げる。計測用スケッチでは `CORE_DEBUG_LEVEL` を下げるか、計測データに固有のプレフィックスを付けてフィルタリングすること。
