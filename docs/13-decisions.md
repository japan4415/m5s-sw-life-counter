## ADR-01: 操作方式 — 外周スライド方式を採用し、タップ方式を却下

### 文脈

円形 AMOLED タッチディスプレイ（466x466px）を持つ M5Stack StopWatch で、2 人のプレイヤーのライフを変更する操作方式を決定する必要があった。初期設計ではタップ方式（画面上の +/- ボタン）を採用していたが、ユーザーから「縁をスライドする操作はどうか / 開始地点によってどちらのライフを変動させるか変える」という提案があり、比較検討を行った。

### 決定

外周スライド方式を採用し、タップ方式を廃止する。

### 比較表

| 項目 | タップ | 外周スライド |
|------|-------|------------|
| ±1の速さ | 高い | やや遅い |
| ±5以上の入力 | 連打が必要 | 1操作で可能 |
| 誤接触への強さ | 弱い | 強い |
| 操作の分かりやすさ | 高い | 説明表示が必要 |
| 物理的な楽しさ | 普通 | 高い |
| 円形画面との相性 | 普通 | 非常によい |
| Undo履歴 | 連打ごとになりやすい | 1スライドを1件にできる |
| 対象プレイヤーの判別 | ボタン位置次第 | 開始地点で明確 |
| 画面中央の視認性 | ±ボタンで狭くなる | ライフ表示を大きくできる |

### 根拠

- 円形画面との相性が非常によく、デバイスの特徴を活かせる
- 誤接触に強く、大会環境での信頼性が高い
- 1 スライドを 1 件として履歴管理でき、Undo が直感的になる
- 画面中央をライフ表示専用にでき、視認性が向上する
- ±5 以上の大きな変動を 1 操作で入力できる

### 影響／トレードオフ

- 操作の分かりやすさが下がるため、初回利用時に説明表示が必要である
- ±1 の入力が僅かに遅い（最低 36 度のスライドが必要）
- タッチ感度・閾値の実機調整が必須である

## ADR-02: UI ライブラリ — LVGL を使わず M5GFX で直接描画

### 文脈

466x466px の円形 AMOLED に描画する方法として、LVGL（組込み向け GUI ライブラリ）と M5GFX（M5Stack 公式グラフィックスライブラリ）を比較した。

### 決定

LVGL を使わず、M5GFX で直接描画する。

### 根拠

本アプリケーションの UI 規模は小さく、画面数も限られている（ゲーム画面、セットアップ画面、メニュー画面、履歴画面）。LVGL のウィジェットシステム・テーマエンジン・イベントモデルは過剰であり、学習コストと依存の複雑さに見合わない。M5GFX は M5Unified と統合されており、`M5Canvas`（PSRAM 上のオフスクリーンバッファ）を使った全画面描画が可能である。

### 影響／トレードオフ

- レイアウト管理やアニメーションを自前で実装する必要がある
- UI が複雑化した場合にスケーラビリティが低い
- M5Stack エコシステムとの親和性は高い

## ADR-03: フレームワーク — MVP は Arduino Framework + M5Unified / M5GFX

### 文脈

ESP32-S3 の開発フレームワークとして Arduino Framework と ESP-IDF を比較した。

### 決定

MVP は Arduino Framework + M5Unified + M5GFX で開発する。将来的に省電力制御やモバイル連携で ESP-IDF への移行がありうる。

### 根拠

M5Unified が Arduino Framework 上でディスプレイ・タッチ・ボタン・振動・電源・バッテリーを統一的に扱える。M5Unified は M5StopWatch を対応デバイスとして掲載している。また、公式に ESP-IDF ベースの StopWatch デモ（`M5StopWatch-UserDemo`）が存在するため、移行パスも確保されている。

### 影響／トレードオフ

- Arduino Framework は ESP-IDF の上に構築されているため、低レベルの制御が必要になった場合に制約がある
- ESP-IDF への移行は大きな作業だが、ドメインロジック層はフレームワーク非依存に設計しておくことで影響を最小化できる

## ADR-04: 永続化 — NVS 16 スロットローテーション

### 文脈

ESP32 の NVS（Non-Volatile Storage）は Flash ベースであり、同一キーへの頻繁な更新は Flash セクタの摩耗を招く。ライフカウンターでは操作ごとに状態を保存する必要がある。

### 決定

NVS に 16 個のスロット（`state_00` 〜 `state_15`）を設け、ローテーションで書き込む。イベントログは LittleFS へ分離する。

### 根拠

- 同一キーの更新継続による NVS 劣化を避けるため、複数スロットをローテーションする
- NVS は頻繁な大容量ログの保存に不向きであるため、イベントログは LittleFS に分離する
- 16 スロットあれば、書き込み途中の電源断でも健全なスロットから復元できる

### 影響／トレードオフ

- スロット管理（sequence 番号の追跡、最新スロットの特定）のロジックが必要になる
- NVS の容量を 16 スロット分消費する
- LittleFS の電源断耐性は別途テストが必要である（要実機確認）

## ADR-05: 通信 — M5Stack から直接クラウドへ接続しない

### 文脈

試合記録をクラウドにバックアップする方法として、M5Stack から直接 HTTPS でクラウド API に接続する方式と、スマホを中継する方式を比較した。

### 決定

M5Stack から直接クラウドへ接続せず、スマホを中継する。

### 根拠

- Tournament Mode の要件として、M5Stack の Wi-Fi を初期化しないことが求められている
- ファームウェアに認証情報・TLS 証明書・Wi-Fi 設定を持ち込みたくない
- M5Stack 単独で全機能が動作することを必須要件としているため、クラウド接続は任意であるべきである

### 影響／トレードオフ

- クラウドへのバックアップにはスマホが必要になる
- スマホが手元にない場合、試合記録は M5Stack のローカルストレージにのみ保存される

## ADR-06: BLE スタック — ESP-NimBLE

### 文脈

ESP32-S3 で BLE を使用する場合、Bluedroid と NimBLE の 2 つのスタックが選択肢となる。

### 決定

ESP-NimBLE を採用する。

### 根拠

NimBLE は Bluedroid と比較してコードサイズとメモリ負荷が小さい。M5Stack StopWatch は PSRAM 8MB を搭載しているが、画面バッファ（約 424 KiB）と他の処理で内部 SRAM を消費するため、BLE スタックのメモリフットプリントは小さい方が望ましい。

### 影響／トレードオフ

- NimBLE は Classic Bluetooth をサポートしない（BLE のみ）。本プロジェクトでは Classic Bluetooth を使用しないため問題ない
- BLE が M5Stack StopWatch の基板上で動作するかは要実機確認である

## ADR-07: シリアライズ — CBOR

### 文脈

BLE 経由でイベントデータをスマホに送信する際のシリアライズ形式を選択する必要があった。

### 決定

CBOR（Concise Binary Object Representation）を採用する。

### 根拠

BLE の MTU は通常 23〜512 bytes であり、データサイズの最小化が重要である。CBOR は JSON と同等の表現力を持ちながらバイナリ形式のためサイズが小さい。

### 影響／トレードオフ

- 人間が直接読めないため、デバッグ時には CBOR → JSON 変換ツールが必要になる
- CBOR のエンコーダ／デコーダライブラリが必要になる（ファームウェア側とスマホ側の双方）

## ADR-08: スマホアプリ — Kotlin Multiplatform

### 文脈

Android と iPhone の両方に対応するスマホアプリの開発方式を選択する必要があった。

### 決定

Kotlin Multiplatform でビジネスロジックを共有し、UI と BLE はネイティブで実装する。Android は Kotlin + Jetpack Compose、iPhone は SwiftUI + CoreBluetooth を使用する。

### 根拠

- ビジネスロジック（イベントモデル、CBOR コーデック、状態復元 Reducer、同期ステートマシン）を 1 箇所で実装・テストできる
- BLE のバックグラウンド処理はプラットフォーム固有の API（Android: `CompanionDeviceManager`、iOS: CoreBluetooth の State Preservation and Restoration）に依存するため、ネイティブ実装が必要である
- UI もプラットフォーム標準に合わせることで、ユーザー体験を損なわない

### 影響／トレードオフ

- 2 つのネイティブ UI を開発・メンテナンスする必要がある
- KMP のビルド環境の構築が必要になる

## ADR-09: 並行性 — MVP は単一の非ブロッキングループ

### 文脈

ファームウェアの並行処理モデルとして、FreeRTOS マルチタスクと単一のイベントループを比較した。

### 決定

MVP は `loop()` 関数による単一の非ブロッキングイベントループで実装する。`delay()` は使用せず、`millis()` または ESP-IDF の単調増加タイマーで時間管理する。

### 根拠

MVP の範囲（ライフ表示・タッチ入力・振動・永続化）では、複雑なマルチタスクは不要である。単一ループの方がデバッグが容易で、競合状態やデッドロックのリスクがない。

### 影響／トレードオフ

- BLE 連携フェーズでは処理の複雑さが増し、マルチタスク（UI Task / Match Engine Task / Event Store Task / BLE Task / Power Task）への移行が必要になる可能性がある
- 単一ループでは長時間ブロックする処理を入れられない

## ADR-10: クラウドは任意

### 文脈

試合記録のバックアップ・共有・統計をクラウドで提供するかを決定する必要があった。

### 決定

クラウドは任意とし、M5Stack 単独で全機能が動作することを必須要件とする。

### 根拠

- 大会環境ではインターネット接続が保証されない
- Tournament Mode では外部通信を行わないことが要件である
- クラウドが停止・廃止されてもデバイス単独で使い続けられることが望ましい

### 影響／トレードオフ

- クラウド同期なしでは、複数端末間でのデータ共有ができない
- 試合共有リンクの生成にはクラウドが必要である

## ADR-11: 既定モードを Tournament Mode とする

### 文脈

通常モード（Casual Mode）と Tournament Mode のどちらをデフォルトにするかを決定する必要があった。

### 決定

既定モードを Tournament Mode とする。

### 根拠

Tournament Mode は通信機能を無効にし、公平性を担保する。大会で使用する際に設定変更を忘れるリスクを排除するため、より制限の強いモードをデフォルトにする。

### 影響／トレードオフ

- カジュアルに使いたいユーザーが Tournament Mode の制約を知らずに困る可能性がある（スマホ連携が使えない等）
- 試合開始後はモード切り替え不可のため、開始時に選択を誤ると試合をやり直す必要がある

## ADR-13: 外周リングの半径に上限を設けない

- 記録日: 2026-08-17
- 状態: 採用

### 文脈

外周スライド方式の操作リングは当初、半径 170〜225px（表示領域 0〜169px の外側、画面の円形表示領域 半径 234px の内側）として設計していた。Phase 0 Step 3/4 の実機タッチ計測（826 サンプル）で、外周を一周なぞるジェスチャーのタッチ座標分布を確認した。

### 決定

外周リングの判定を「半径 165px 以上」とし、上限を設けない。表示領域は 0〜164px、キャンセル半径 145px は据え置きとする。

### 根拠

- 826 サンプル中、半径 170〜226px に収まったのは 608 件（73.6%）のみ。外側へのはみ出しが 205 件（24.8%）あり、上限を設けると正当な操作の約 4 分の 1 を棄却してしまう
- タッチ IC（CST820B）は表示円（半径 234px）より外側の座標も返す（117 サンプルが該当）。実測タッチ半径の最大値は 268.2 であった
- 座標範囲は x 18〜465、y 14〜466 であり、物理的なタッチ可能領域は表示領域より広い

### 影響／トレードオフ

- 画面外縁より外側の誤接触（端を持った際の意図しないタッチなど）もリング入力として扱われる。ただし、キャンセル半径（145px）への引き込みと、開始禁止領域（左右各 20 度）で一定の誤操作防止は維持される
- 内側の閾値を 170px から 165px に引き下げたことで、表示領域との隙間が 1px に縮小し、表示領域へのタッチがリング操作として誤検出される可能性がわずかに増加する

## ADR-14: ジャンプ除外を絶対角度から角速度判定に変更

- 記録日: 2026-08-17
- 状態: 採用

### 文脈

外周スライド方式では、タッチ座標のノイズや指の跳ねによる不正な角度変化を除外する必要がある。当初の設計では「1 サンプルあたり 30 度以上のジャンプを無視する」という絶対角度方式を採用していた。Phase 0 Step 3/4 の実機タッチ計測で、サンプリング間隔の実態を確認した。

### 決定

ジャンプ除外の判定を絶対角度方式から角速度方式に変更する。`abs(deltaDeg) / deltaMs` を計算し、しきい値を超えた場合にそのサンプルを無視する。しきい値の初期提案値は 0.7 度/ms（700 度/秒）とする。

### 根拠

- タッチのサンプリング間隔は中央値 15 ms（約 66 Hz）だが、最大 270 ms の欠測が発生する
- 実測の角速度は約 233 度/秒であり、270 ms の欠測後に約 63 度の正当な角度変化が生じうる。絶対角度方式（30 度/サンプル）ではこれを誤って棄却してしまう
- 角速度方式であれば、欠測時間を考慮した判定が可能であり、正当な操作を棄却するリスクが低い

### 影響／トレードオフ

- しきい値（0.7 度/ms）は初期提案値であり、実機での調整が必要である。この値自体は未検証
- 時間解像度（`millis()` の精度）に依存するため、極端に短い間隔（1 ms 以下）では判定が不安定になる可能性がある
- 絶対角度方式と比較して計算量がわずかに増加する（除算が追加される）

## ADR-15: MVP の描画方式を全画面転送から部分再描画に変更

- 記録日: 2026-08-17
- 状態: 採用

### 文脈

MVP の描画方式は当初、PSRAM 上の全画面 Canvas（468x468x16bit）を毎フレーム AMOLED に転送する全画面転送方式を想定していた。Phase 0 Step 8 の実機計測で描画レートを実測したところ、全画面転送の中央値は 44,639 us（22.4 FPS）であった。一方、外周スライド操作中のライフ表示更新間隔は約 43 ms である（実測スイープ角速度 233 度/秒、感度 10 度/ライフから算出）。全画面転送 44.6 ms ではこの更新間隔を超過し、ライフ変更のたびに描画が間に合わなくなる。

### 決定

MVP の描画方式を全画面転送から部分再描画に変更する。変更が生じた領域のみを Canvas に描画し、部分的に転送する。

### 根拠

- 全画面転送（468x468）の所要時間 44,639 us に対し、ライフ表示の更新間隔が約 43 ms であり、描画予算を超過する
- 上半分（468x234）の転送は 22,312 us（44.8 FPS）、中央 200x120 の転送は 4,994 us（200.2 FPS）であり、部分再描画であれば十分な描画予算が確保できる
- 外周スライド操作中に変化するのはライフ数値とプレビュー表示のみであり、背景や外周リングの再描画は不要である

### 影響／トレードオフ

- 差分管理（dirty region tracking）の実装が必要になり、描画ロジックの複雑さが増す
- 画面全体のレイアウト変更（画面遷移など）では引き続き全画面転送が必要であり、2 つの描画パスを持つことになる
- 部分再描画の描画予算が 154 ms 以内に収まり続けることを回帰テストで確認する必要がある（L2 テスト項目として追加）

**事後注記（2026-08-18）**: 感度が 36 度/ライフに変更されたこと（ADR-18）により、ライフ表示の更新間隔は約 154 ms に延長された。全画面転送（44.6 ms）でも 154 ms の予算内に収まるようになったが、本 ADR の決定（部分再描画の採用）は覆さない。理由: タッチのサンプリングは 15 ms 間隔で到来するため描画以外の処理に余地が必要であること、将来の感度変更で予算が縮む可能性があること。詳細は [アーキテクチャ](./07-architecture.md) の描画予算の節を参照。

## ADR-16: 振動の強度を 255 固定とし、強弱は時間の長短で表現

- 記録日: 2026-08-17
- 状態: 採用

### 文脈

設計書では振動の強弱を `M5.Power.setVibration()` の引数（0〜255）で制御し、ライフ通過時の軽い触覚フィードバック（弱い振動）とライフ 0 到達時の警告（強い振動）を使い分ける想定であった。Phase 0 Step 5 の実機計測で振動の体感を確認したところ、この想定が実測で否定された。

`M5.Power.setVibration(uint8_t)` の引数は強度（0〜255）であり、`setVibration(0)` を書くまで振動は止まらない。実装は M5IOE1 の `pwm_ch1`（GPIO9）への 12bit PWM である。

### 決定

振動の強度を 255 固定とし、振動の強弱の表現は時間の長短で行う。

### 根拠

- 実測で強度 32〜192 は体感できず、255 でのみ体感できた
- 強度 255 において、15 ms はかろうじて体感でき、20 ms で確実に体感できた
- 強度による段階的な振動表現が物理的に成立しないため、時間の長短で代替する

### 影響／トレードオフ

- 設計書が想定していた「弱い警告振動」（ライフ通過時の軽いフィードバック）のような強度段階の表現力が失われる
- 振動のオン・オフ（255 と 0 の切り替え）をタイマーで管理する実装が必要になる
- 指定時間経過後に `setVibration(0)` を確実に呼ぶ仕組みが必要であり、呼び忘れると振動が止まらなくなる

## ADR-17: 振動の間引きを必須要件に格上げ（方式決定済み: 案 B）

- 記録日: 2026-08-17
- 方式決定日: 2026-08-18
- 状態: 採用（方式解決済み: 案 B — 感度引き下げ）

### 文脈

設計書では振動の間引きを「MVP 後に検討する任意の改善項目」として位置付けていた。Phase 0 Step 5/8 の実測結果により、この前提が崩れた。

外周スライド操作中のライフ表示更新間隔は、旧感度 10 度/ライフの場合で約 43 ms（スイープ角速度 233 度/秒）である。ADR-16 により振動の最低体感時間は 20 ms と確定した。43 ms 間隔に 20 ms パルスを入れるとデューティ比は約 47% となり、ライフ 1 段階ごとのクリック感ではなく連続振動と体感される。

### 決定

振動の間引きを必須要件に格上げする。~~ただし、間引きの具体的な方式は未決定であり、以下の 2 つの候補がある:~~

**方式決定（2026-08-18）**: Phase 1 実機評価により **案 B（感度引き下げ）** が選ばれた。感度を 10 度/ライフから 36 度/ライフに変更したこと（ADR-18）により、ライフ 1 段階あたりの時間が約 43 ms から約 154 ms に延長され、デューティ比が約 47% から約 13% に低下した。デューティ 13% は十分にクリック感として体感でき、間引きは不要になった。

検討された 2 案:

1. **案 A. 間引き方式**: ライフ段階ごとの振動パルスを N 段階に 1 回に間引く（例: 3 段階に 1 回のみ振動） → 不採用
2. **案 B. 感度引き下げ**: 感度を 10 度/ライフから引き下げてライフ更新間隔を広げ、パルス間の無音区間を確保する → **採用**

**実装上の扱い**: `src/infra/haptics_m5.cpp` の間引きロジックは削除せず `kStepThrottleEnabled = false` で無効化してある。将来、感度を上げ直した場合に間引きを再有効化できるようにするためである。

### 根拠

- 旧感度 10 度/ライフでは 43 ms 間隔に 20 ms パルスでデューティ比約 47% となり、連続振動でクリック感として機能しなかった
- 感度 36 度/ライフ（ADR-18）では 154 ms 間隔に 20 ms パルスでデューティ比約 13% となり、間引きなしでもクリック感が得られる
- 案 B は案 A より実装がシンプルであり、均一なフィードバックを提供できる
- 間引きなしでは 10 ライフ以上の変動で不快な連続振動になることが予測されたが、感度 36 度/ライフではこの問題は発生しない

### 影響／トレードオフ

- ~~間引き方式を採る場合、間引きロジック（パルスカウンタとスキップ判定）の実装が必要になる~~（案 A は不採用）
- 感度引き下げにより、一周で変更できるライフ数が 36 から 10 に減少し、大きなライフ変動に複数周回が必要になる（ADR-18 で詳述）
- いずれの方式でも、ライフ 0 到達時の警告振動（長い振動パルス）は間引きの対象外とし、確実に体感させる必要がある
- ~~具体的な方式の選定が Phase 1 のブロッカーとなる可能性がある~~（解決済み）

## ADR-18: 感度を一周 10 ライフ（36 度/ライフ）とする

- 記録日: 2026-08-18
- 状態: 採用

### 文脈

Phase 1 の実装を実機で操作し、外周スライドの感度の妥当性を評価した。旧設計値 10 度/ライフ（一周 360 度 = 36 ライフ分）で実機を操作したところ、ユーザーから「速すぎる。一周で 10 にしてほしい」という評価があった。実測のスイープ角速度は約 233 度/秒であり、旧設計値ではライフ 1 段階あたり約 43 ms（233 度/秒 / 10 度 ≒ 23.3 段階/秒 → 1 段階あたり約 43 ms）で到達し、意図しない大量入力が発生しやすかった。

### 決定

感度を **36 度/ライフ**（一周 360 度 = **10 ライフ分**）に設定する。`kDegreesPerLife` を 10.0f から 36.0f に変更した。

### 根拠

- 旧値 10 度/ライフ（一周 36 ライフ）は実機操作で「速すぎる」と評価された
- 36 度/ライフ（一周 10 ライフ）では、ライフ 1 段階あたり約 154 ms で到達し、意図的な操作感が得られる
- 副次的効果として、振動のデューティ比が約 47% から約 13% に低下し、間引きが不要になった（ADR-17 の方式決定に直結）
- ユーザー評価では「ちょうど良い」と評価された

### 影響／トレードオフ

- FaB の初期ライフ 40 をゼロにするには 1,440 度（4 周）のスライドが必要になる（旧値では約 1.1 周）
- 20 点の変更に 720 度（2 周）が必要（旧値では 200 度）
- 実測の快適なスイープ所要時間は一周あたり約 2.9〜3.5 秒であるため、40→0 の操作には約 12〜14 秒を要する
- この操作コストはユーザー評価で「ちょうど良い」と許容された。大きな値の変更は Set Life メニューによる直接入力でも対応可能である
- 将来、加速機構（速度や累積角に応じて感度を動的に変更する）を追加する余地がある

## ADR-19: メニュー操作をボタンのみで行う（タッチを使わない）

- 記録日: 2026-08-18
- 状態: 採用

### 文脈

ゲームメニュー（5 項目。当初は 8 項目だったが Sleep 廃止（ADR-24）、New Game 統合（ADR-25）、Swap Sides 削除（ADR-26）により削減）の操作方法を決定する必要があった。タッチで項目をタップする方式と、物理ボタンのみで操作する方式が候補にあった。

### 決定

メニュー操作はボタンのみで行い、タッチは使用しない。A 短押しで次の項目へ移動（循環）、B 短押しで決定、A+B 長押し（1 秒）でメニューを閉じる、B 長押し（1 秒）で Rematch の確認を確定する。

### 根拠

- ボタンは 2 個しかなく、短押し・長押し・同時押しの組み合わせで十分なメニュー操作が可能
- タッチロック中でもメニュー操作ができる必要がある。タッチでメニューを操作すると、ロック中にメニューが使えなくなる
- メニュー画面でのタッチ操作は誤操作のリスクが高い（タッチロックの解除直後に意図しないメニュー操作が発生しうる）

### 影響／トレードオフ

- ボタン 2 個で 5 項目のメニューを操作するため、目的の項目に到達するまでに最大 4 回の A 短押しが必要（当初は 8 項目・最大 7 回だったが、ADR-24 / ADR-25 / ADR-26 により削減）
- メニュー画面での長押し操作（閉じる、確認確定）が短押しと同じ書式で表記されると誤解を招く。`A+B(hold)=Close` のように長押しであることを明示する表記を採用した

## ADR-20: 長押しを 1000 ms（1 秒）に統一

- 記録日: 2026-08-18
- 状態: 採用

### 文脈

長押し操作のしきい値を決定する必要があった。当初は A+B 同時長押しを 2000 ms、単独長押しを 1500 ms で設計していた。Phase 2 の実機評価で「長すぎる」と判断され、1500 ms に統一。さらに「まだ長い」との評価を受け、最終的に 1000 ms に短縮して確定した。

### 決定

すべての長押し操作（A+B 同時、A 単独、B 単独）のしきい値を **1000 ms（1 秒）に統一**する。

### 根拠

- 実機評価で 2000 ms、1500 ms はいずれも「長い」と評価された
- 1000 ms は「押しているという意思を示すのに十分で、待たされる感覚がない」と評価された
- すべての長押しを同じ値にすることで、ユーザーが覚えるべきタイミングが 1 つになり学習コストが下がる

### 影響／トレードオフ

- **A を押してから 1 秒以内に B を押さないと A+B 長押し（メニュー起動）にならない**: 単独長押しと A+B 長押しのしきい値が同じ 1000 ms のため、A を 1 秒以上押し続けると A 単独長押しが先に成立する。現在 A 単独長押しにはどの画面でも動作を割り当てていないため実害はないが、将来 A 単独長押しに機能を割り当てた場合に問題になりうる
- 誤操作のリスクが 1500 ms / 2000 ms 時代より僅かに上がるが、長押し進捗の表示（弧とテキスト）により、ユーザーが自分の操作状態を常に確認できるため許容される

## ADR-21: 初期ライフ設定を外周スライド方式にする

- 記録日: 2026-08-18
- 状態: 採用

### 文脈

初期ライフの設定方法を決定する必要があった。旧設計では `[20] [40] [CUSTOM]` をタッチで選択し、`[ START ]` を長押しで確定する方式だった。実装段階で、外周スライド（製品の中心操作）をそのまま再利用する方式に変更した。

### 決定

初期ライフ設定画面では外周スライドで各プレイヤーの開始ライフを直接増減する。上半分のスライドは相手の開始ライフ、下半分のスライドは自分の開始ライフを操作する。A 短押しで上下両方を 20 / 40 のプリセットにトグルする。B 長押し（1 秒）で試合を開始する。

### 根拠

- 外周スライドという製品の中心操作をそのまま再利用でき、ユーザーが新しい操作を覚える必要がない
- CUSTOM 値（任意値）も同じスライド操作で直感的に入力できる。旧方式では CUSTOM 選択後に別の入力 UI が必要だった
- プリセット（20 / 40）は A ボタンの短押し 1 回で切り替えられ、よく使う値への到達が速い

### 影響／トレードオフ

- 40 から大きく異なる値（例: 100）を設定する場合、外周スライドで多数回のスライドが必要になる
- 旧方式のようにタッチで一覧から選ぶ直感性は失われるが、操作の一貫性が向上する

## ADR-22: スリープをメニュー項目で提供する

- 記録日: 2026-08-18
- 状態: ADR-24 で廃止（superseded by ADR-24）

### 文脈

スリープ機能の起動方法を決定する必要があった。一般的なデバイスでは電源ボタンの短押しでスリープに入るが、M5Stack StopWatch では電源ボタンの押下をアプリケーションから検出できないことが判明した（M5Unified が M5PM1 の IRQ ピン GPIO12 を設定しないため、`getKeyState()` でボタン押下を取得できない）。

### 決定

スリープ機能をゲームメニューの項目（Sleep）として提供する。B 短押しで選択するとライトスリープに入る。確認ダイアログは不要とする（ライトスリープは可逆操作であり、ボタン押下または 30 秒タイマーで即座に復帰できるため）。

### 根拠

- 電源ボタンの押下検出が技術的に不可能であるため、既存のメニュー UI を活用するのが最も自然な代替手段である
- ゲームメニューは A+B 長押し 1 秒で開くため、Sleep に入るまでに「メニューを開く → Sleep に移動 → 決定」の 3 ステップが必要であり、意図しないスリープのリスクは低い
- 確認なしで即座にスリープに入ることで、操作のテンポを損なわない

### 影響／トレードオフ

- **電源ボタンを押す本来の操作感にはならない**: 物理ボタン 1 つでスリープに入るのではなく、メニューを経由する必要がある。大会中にすばやくスリープさせたい場面では操作ステップが多い
- メニュー項目が 7 → 8 に増え、項目間隔を 24px → 22px に詰める調整が必要だった
- 復帰後にメニュー画面が表示される（Sleep を選択した時点の画面状態がそのまま維持される）

## ADR-23: ライトスリープのみを使い、復帰手段を 2 つ用意する

- 記録日: 2026-08-18
- 状態: ADR-24 で廃止（superseded by ADR-24）

### 文脈

スリープの実装方式を決定する必要があった。ESP32-S3 には `esp_light_sleep_start()`（ライトスリープ）と `esp_deep_sleep_start()`（ディープスリープ）がある。また、M5Unified が提供する `M5.Power.powerOff()` / `M5.Power.timerSleep()` もある。

実機での試行中に、GPIO ウェイクアップのみでライトスリープを実装したところ、**ESP32-S3 の GPIO スリープ設定の問題によりスリープから復帰できず、USB シリアルも消失して書き込み不能になる事故が発生した**。電源ボタン長押しでダウンロードモードに入れて復旧する必要があった。原因は M5Unified（M5GFX）の `pinMode(INPUT)` がスリープ時プルアップ（SLP_PU）をクリアするため、スリープ中にボタンのピンがフローティングになり LOW（押下）を検出できなくなることだった。

### 決定

1. **ライトスリープのみを使い、ディープスリープ / powerOff / timerSleep は使わない**: ライトスリープは RAM を保持するため、永続化（Phase 3）が未実装でも試合状態を失わない
2. **復帰手段を必ず 2 つ用意する**（GPIO ウェイクアップ＋30 秒タイマーウェイクアップ）: GPIO ウェイクアップが効かない場合でもタイマーで復帰できるようにする

### 根拠

- **RAM 保持の必要性**: `deepSleep` / `powerOff` は RAM を失うため、永続化が実装されていない現段階では試合状態が消失する。`lightSleep` だけが RAM を保持する
- **復帰不能事故の教訓**: GPIO ウェイクアップのみに依存した場合、ピン設定の問題で復帰できなくなると USB シリアルも消失し、通常の書き込みが不可能になった。タイマー復帰を安全策として併用していれば、この事故は防げた
- **SLP_SEL の対処**: `gpio_sleep_sel_dis(pin)` で SLP_SEL を無効化し、通常時の GPIO 設定をスリープ中も維持することで、ボタンのプルアップが保持され GPIO ウェイクアップが正常に機能する。ただし、この対処が将来の環境変化（ライブラリ更新等）で無効になるリスクがあるため、タイマー復帰の安全策は維持する

### 影響／トレードオフ

- ライトスリープはディープスリープと比較して消費電力が高い。バッテリー節約の観点ではディープスリープが望ましいが、Phase 3 で永続化が実装されるまではライトスリープを使うことを優先する
- 30 秒タイマー復帰は安全策として必要だが、「30 秒後に勝手に画面が点く」という動作をユーザーが予期しない可能性がある。ただし、スリープに入ったこと自体をユーザーが認識しているため、実用上の混乱は小さいと判断した
- Phase 3 で NVS への永続化が実装された後は、ディープスリープの採用を再検討できる。その場合も復帰手段を 2 つ用意する方針は維持する

---

## ADR-24: NVS 永続化の導入とスリープ機能の廃止

- 記録日: 2026-08-18
- 状態: 採用

### 文脈

issue #19 で「電源ボタン長押しで電源が落ちない」という報告があった。実際には電源ボタン長押し（約 2 秒）はダウンロードモードへの移行であり、電源 OFF は「素早く 2 回押し」が公式仕様である（[docs/01-hardware.md](./01-hardware.md)、出典: https://docs.m5stack.com/en/core/StopWatch ）。しかし、電源 OFF すると RAM 上の MatchState が消失するため、ユーザーは試合中に電源を落とせないという問題があった。

スリープ機能（ADR-22 / ADR-23）は、この「電源 OFF で試合状態が消える」ことの回避策として、永続化が未実装であることを前提に導入されたものである。ライトスリープは RAM を保持するため、電源を完全に落とさずに消費電力を下げつつ試合状態を維持する手段として設計された。

一方で、M5Unified が M5PM1 の IRQ ピン（GPIO12）を設定しないため、アプリケーションから電源ボタンの押下を検出できない。そのためスリープはメニュー項目として提供し（ADR-22）、復帰手段として GPIO ウェイクアップと 30 秒タイマーの 2 つを用意した（ADR-23）。

今回 NVS による永続化を実装したことで、スリープ機能の前提（永続化が未実装であること）が消えた。

### 決定

1. **NVS で MatchState を永続化する**: 名前空間 `lifectr`、16 スロットローテーション（ADR-04 の設計に基づく）、CRC32 検証付きで MatchState を NVS に保存する
2. **スリープ機能を廃止する**: メニューの Sleep 項目と `enterLightSleep()` の実装を削除する
3. **電源 OFF は公式仕様の「素早く 2 回押し」を案内する**: ユーザー向けドキュメントに電源 ON/OFF 操作を主動線で記載する
4. **電源 ON 時に NVS から自動復元する**: 確認ダイアログは挟まず、前回の試合状態をそのまま復元する。新規試合を開始したい場合はメニューの Rematch または Set Life を使用する

### 根拠

- **永続化により RAM 保持が不要になった**: NVS に MatchState を保存することで、電源 OFF でも試合状態が失われない。ライトスリープで RAM を保持する必要がなくなった
- **ライトスリープの消費電力**: ライトスリープは deepSleep / powerOff より消費電力が大きい。バッテリー容量 450mAh のデバイスにおいて、ライトスリープで待機させるよりも電源 OFF の方がバッテリー消費を抑えられる
- **復帰操作の分かりにくさ**: ライトスリープからの復帰は A/B ボタン押下または 30 秒タイマーであり、電源ボタンとは別の操作系統である。電源 OFF/ON（電源ボタンの操作）に統一する方が分かりやすい
- **スリープの存在意義の消失**: スリープ機能は永続化未実装を前提とした回避策であった。前提が消えた以上、機能を残すことは二重の複雑さを抱えるだけである

### 却下した代替案

1. **スリープを残して NVS 保存も追加する**: スリープの存在意義が消えており、両方を維持すると二重の複雑さになる。メニュー項目が増え、ユーザーに「Sleep と電源 OFF の違い」を説明する必要が生じる
2. **起動時に「前回の試合を再開しますか」確認ダイアログを出す**: 電源 ON から即ゲーム画面に遷移する UX を損ねる。新規試合を開始したい場合はメニューの Rematch または Set Life で対応でき、確認ダイアログは不要である
3. **M5PM1 の IRQ ピンを自前設定して電源ボタン長押しを検出する**: M5Unified が想定していない使い方であり、ライブラリ更新時の互換性リスクと保守コストが高い。電源ボタンの検出が可能になったとしても、スリープ機能の存在意義は永続化により消えているため、根本的な解決にならない

### 影響／トレードオフ

- **メニュー項目が 8 から 5 に減る**: Sleep 項目の削除、New Game の Rematch 統合（ADR-25、#15）、および Swap Sides の削除（ADR-26、#16）により、項目間隔を 24px（`theme::kMenuItemSpacing`）で確定した。5 項目の y 範囲は 157〜253 となる
- **削除されるコード**: `enterLightSleep()` とその周辺（GPIO wakeup 設定、`gpio_sleep_sel_dis()` による SLP_SEL 無効化、30 秒安全タイマー、`wakeInputSuppressed_` 等）が削除される
- **ユーザー向けドキュメントの更新が必要**: 電源 ON/OFF 操作（短押し 1 回 = ON/リセット、素早く 2 回 = OFF）を主動線で記載し、電源 OFF しても試合状態は保持されることを明記する必要がある
- **NVS 書き込みの Flash 摩耗**: 操作ごとに NVS へ書き込むため Flash セクタの摩耗が発生する。ただし 16 スロットローテーション（ADR-04）により単一キーへの集中書き込みを回避しており、実用上の寿命は十分である

## ADR-25: New Game を Rematch に統合

- 記録日: 2026-08-19
- 状態: 採用

### 文脈

メニューには Rematch（同じ開始ライフで試合をやり直す）と New Game（開始ライフを変更して新しい試合を始める）の 2 つの項目が存在していた。しかし、New Game の挙動は「Set Life で Setup 画面へ遷移し、開始ライフを変更して B 長押しで試合を開始する」であり、Set Life メニュー項目と実質的に同じ経路をたどっていた。

### 決定

1. **New Game メニュー項目を削除し、Rematch に統合する**: 同じ開始ライフでの試合やり直しは Rematch が担い、開始ライフを変更して新しい試合を始める場合は Set Life を使用する
2. **メニュー項目を 7 から 6 に削減する**: 項目順は Resume / History / SetLife / Rematch / SwapSides / About となる（その後 ADR-26 で SwapSides も削除され 5 項目となった）
3. **SwapSides と About のインデックスが繰り上がる**: SwapSides は 5→4、About は 6→5 に変更される（その後 ADR-26 で SwapSides が削除され About は 4 となった）

### 根拠

- **New Game と Rematch の挙動が実質同一だった**: New Game は開始ライフを変更できる点が Rematch と異なっていたが、この機能は Set Life メニュー項目が既に担っている
- **Set Life が開始ライフ変更の唯一の経路になる**: Set Life は Setup 画面へ遷移し、現在のプレイライフを起点に開始ライフを変更できる。New Game を廃止しても、開始ライフ変更→試合開始のユースケースは Set Life で完全にカバーされる
- **メニュー項目の削減**: 7→6 項目に減ることで、項目間隔に余裕が生まれ、操作回数も最大 6 回から 5 回に減る（その後 ADR-26 で 5 項目・最大 4 回に削減）

### 影響／トレードオフ

- **`kMenuItemCount` が 7 から 6 に変更**: `MenuItem` 列挙から `NewGame` が削除され、`SwapSides` と `About` のインデックスが繰り上がる（その後 ADR-26 で `SwapSides` も削除され 5 に変更）
- **テストコードの更新が必要**: メニューインデックスに依存するテストケースの修正が必要
- **ドキュメントの更新が必要**: UI/UX 設計（画面遷移図・メニュー項目一覧）、要件定義（FR-13 / FR-15）、ADR-19 / ADR-24 の項目数記述を更新する

## ADR-26: Swap Sides を削除

- 記録日: 2026-08-19
- 状態: 採用

### 文脈

メニューに Swap Sides（上下プレイヤーの入れ替え）が存在していたが、実運用で使用されていなかった。対面対戦のカードゲーム（FaB）では座席位置が物理的に固定されており、画面上の上下を入れ替える必要がない。

### 決定

1. **Swap Sides メニュー項目を削除する**: `MenuItem` 列挙から `SwapSides` を削除し、`kMenuItemCount` を 6 から 5 に変更する
2. **`ScreenAction::SwapSides` を削除する**: アプリ層で dispatch する必要がなくなるため
3. **`domain::swapSides()` 関数を削除する**: 呼び出し元がなくなるため

### 根拠

- **実運用で不要**: 対面対戦では物理的な座席位置が決まっており、画面上の上下を入れ替える場面がない
- **メニュー項目の削減**: 6→5 項目に減ることで、操作回数が最大 5 回から 4 回に減る
- **New Game 削除（ADR-25）と同じ方針**: 使用しない機能を削除してメニューを簡素化する

### 影響／トレードオフ

- **`kMenuItemCount` が 6 から 5 に変更**: `MenuItem` 列挙から `SwapSides` が削除され、`About` のインデックスが 5→4 に繰り上がる
- **テストコードの更新が必要**: `domain::swapSides()` を呼び出すテストケースと、メニューインデックスに依存するテストケースの修正が必要
- **ドキュメントの更新が必要**: UI/UX 設計（画面遷移図・メニュー項目一覧）、要件定義（FR-16）、ADR-19 / ADR-24 / ADR-25 の項目数記述を更新する

## Phase 0 実地知見

Phase 0 の作業中に判明した実務上の知見を記録する。記録日: 2026-08-17。

1. **`uv tool install platformio` は `--with pip` が必須。** PlatformIO が内部で `python -m pip` を呼ぶため、pip の無い uv ツール環境では `MissingPackageManifestError` で失敗する。

2. **`pio device monitor` は TTY を要求するため非対話環境では動かない**（`termios.error: (19, 'Operation not supported by device')`）。シリアル出力の確認には pyserial で直接ポートを開いて読む必要がある。

3. **Native USB-CDC ではチップのリセットで USB が再列挙され、開いていたポートハンドルが無効になる。** `setup()` で 1 回だけ出力する診断スケッチは取りこぼしやすいため、`loop()` から定期出力する作りが確実。

4. **ダウンロードモード中はアプリが動かない。** 長押しでダウンロードモードに入れたままだとシリアルは完全に無音になり、「アプリのクラッシュ」と区別がつかない。切り分け時はまず電源ボタン短押しで通常起動させること。

5. **`/dev/cu.usbmodem*` は ESP32-S3 の ROM が常時提供する USB Serial/JTAG であり、ポートの存在はアプリが動いている証拠にならない。**

6. **M5GFX は StopWatch を I2C プローブで自動判別する**（GPIO47=SDA / GPIO48=SCL、RX8130 0x32・BMI270 0x68・CST820 0x15 の存在で判定）。ビルド時マクロによるボード固定は不要。

7. **公式 `platformio.ini` には `M5PM1`（電源管理 IC）と `M5IOE1`（IO エキスパンダ）のライブラリが含まれる。** AMOLED・バイブは M5IOE1 配下の電源レール L3B にぶら下がる。

8. **公式のファクトリーリストア手順に「書き込み完了後、デバイスのリセットボタンを押す」と明記がある。**

9. **計測用スケッチは機械解析しやすい固定フォーマットで出力する。** `T,<millis>,<x>,<y>,<radius>,<deg>` 形式の 1 行 1 サンプル、ジェスチャー間の区切りマーカー、画面上の方位ガイド（N/E/S/W）を含めると、ログの後処理（CSV パース、統計計算）が容易になる。自由形式のテキスト出力は後から解析しづらい。

10. **`setVibration()` の引数は強度（0〜255）であり、時間ではない。** `M5.Power.setVibration(uint8_t)` の引数を時間（ミリ秒）と取り違えると、`setVibration(0)` を呼ぶまで振動が止まらず「振動していない」と誤診する。実装は M5IOE1 の `pwm_ch1`（GPIO9）への 12bit PWM である。API の引数の意味は公式ソースコードで必ず確認すること。

11. **`-DCORE_DEBUG_LEVEL=5` は起動時に I2C ログを大量に出力する。** M5GFX の自動判別が I2C プローブを多数行うため、デバッグレベル最大ではシリアルに大量のログが流れ、計測値の読み取りを妨げる。計測用スケッチでは `CORE_DEBUG_LEVEL` を下げるか、計測データに固有のプレフィックスを付けてフィルタリングすること。

### スリープ実装時の事故と原因

ライトスリープを GPIO ウェイクアップのみで実装して実機に書き込んだところ、以下の事故が発生した:

1. **ライトスリープに入った後、ボタンを押しても復帰しなかった**
2. **USB シリアルも消失し、PlatformIO からの書き込みが不可能になった**
3. **電源ボタン長押し（約 2 秒）でダウンロードモードに入れて復旧した**

**原因**: ESP32-S3 のライトスリープでは、既定で GPIO がスリープ用レジスタ（SLP_*）の設定に切り替わる。M5Unified（M5GFX）の `pinMode(INPUT)` はスリープ時プルアップ（SLP_PU）をクリアするため、スリープ中にボタンのピン（GPIO 1, GPIO 2）がフローティングになり、ボタン押下（LOW）を検出できなかった。

**対処**: `gpio_sleep_sel_dis(pin)` で SLP_SEL を無効化し、通常時の GPIO 設定をスリープ中も維持するようにした。あわせて `gpio_set_direction(INPUT)` と `gpio_pullup_en()` を明示的に呼ぶ。

**教訓**: スリープには必ず復帰手段を 2 つ用意する（GPIO ウェイクアップ＋タイマーウェイクアップ）。復帰手段が 1 つだけの場合、それが効かない時点で書き込みもできなくなる（ADR-23）。

### 新たに判明した知見

| 知見 | 詳細 |
|------|------|
| 電源ボタンはアプリから検出不可 | M5Unified が M5PM1 の IRQ ピン（GPIO12）を設定しないため。コード中にその旨の注記あり |
| ボタンは GPIO 直結 | KEYA=GPIO2 / KEYB=GPIO1。M5IOE1 経由ではない（`board_M5StopWatch` 分岐で確認） |
| USB 給電判定手段が判明 | `getVBUSVoltage()` で判定可能（USB 時 約 4800〜5100 mV、未接続時 約 0 mV）。`getPowerSource()` も使用可能。実装には未適用 |
| M5GFX の標準フォントで絵文字は出ない | バッテリーアイコンは図形描画で対応 |
