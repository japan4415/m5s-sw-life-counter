FaB ライフカウンターの永続化設計を記述する。NVS による試合状態の永続化は実装済みであり、電源断・再起動後に直前のゲームを自動復元する。将来フェーズでのイベントログ設計（LittleFS）も併せて記載する。

## 保存の目的と要件

永続化の目的は、**電源断・再起動後に直前のゲームを復元する**ことである。

許容する損失は**「確定途中だった最後の 1 操作」のみ**とする。具体的には:

- 外周スライド中（まだ指を離していない）に電源が落ちた場合、そのスライドの変更は失われてよい
- 確定済み（指を離して `commitGesture` が完了した）操作は、次回起動時に復元されなければならない

---

## 保存対象

以下のデータを永続化する:

| 保存対象 | 型 | 説明 |
|---|---|---|
| 現在ライフ（Top） | `uint32_t` | 上側プレイヤーの現在ライフ |
| 現在ライフ（Bottom） | `uint32_t` | 下側プレイヤーの現在ライフ |
| 開始ライフ（Top） | `uint32_t` | 上側プレイヤーの開始ライフ |
| 開始ライフ（Bottom） | `uint32_t` | 下側プレイヤーの開始ライフ |
| 上下プレイヤーの対応 | -- | `players[0]` = Top、`players[1]` = Bottom の対応関係 |
| タッチロック状態 | `bool` | タッチロックの ON/OFF |
| 直近 64 件の変更履歴 | `RingBuffer<LifeChange, 64>` | Undo に必要な履歴データ |
| ゲーム進行中フラグ | `bool` | ゲームがアクティブかどうか |
| スキーマバージョン | `uint16_t` | データ形式のバージョン番号 |

## NVS 16 スロットローテーション（実装済み）

### 概要

Arduino の `Preferences` API を使用して NVS（Non-Volatile Storage）にバイナリ Blob として保存する。名前空間は `lifectr`、キーは `s00` から `s15` の 16 スロットを使用する。

### スロットローテーション

保存のたびに次のスロットへ書き込み先を進める。

**同じキーを更新し続けると NVS が劣化する。** NVS は内部的にページ単位で管理されており、同一キーへの頻繁な書き込みはページの使い切りとガベージコレクションを加速させる。16 スロットのローテーションにより、各スロットへの書き込み頻度を 1/16 に低減する。

### PersistentRecord 構造体

```cpp
struct PersistentRecord {
    uint32_t magic;
    uint16_t schemaVersion;
    uint16_t payloadSize;
    uint32_t sequence;
    MatchState state;
    uint32_t crc32;
};
```

| フィールド | 型 | 意味 |
|---|---|---|
| `magic` | `uint32_t` | 固定値。有効なレコードであることを識別する |
| `schemaVersion` | `uint16_t` | データ形式のバージョン番号 |
| `payloadSize` | `uint16_t` | `state` フィールドのバイト数 |
| `sequence` | `uint32_t` | 単調増加する書き込み通し番号。最新レコードの特定に使用する |
| `state` | `MatchState` | 保存対象のゲーム状態全体 |
| `crc32` | `uint32_t` | `magic` から `state` までの CRC-32 チェックサム |

## 起動時の復元アルゴリズム（実装済み）

起動時に以下の手順で最新の有効なレコードを検出し、確認ダイアログなしでゲーム状態を自動復元する:

1. `s00` から `s15` まで全 16 スロットを順に読み込む
2. 各スロットについて以下の検証を行う:
   - `magic` が期待する固定値に一致するか
   - `schemaVersion` が現在のファームウェアで対応している範囲内か
   - `payloadSize` が `MatchState` の期待サイズに一致するか
   - `magic` から `state` までの CRC-32 を再計算し、`crc32` フィールドと一致するか
3. 検証に失敗したスロットはスキップし、全検証に合格したスロットの中から `sequence` が最大のレコードを採用する（スキャンは一巡で完了する）
4. 有効なレコードが見つかった場合、確認ダイアログなしで直接ゲーム画面（ACTIVE 状態）に復帰する
5. 全スロットが検証に失敗した場合、保存データなしとして新規ゲーム設定画面へ遷移する

この手順により、書き込み途中で電源が落ちた場合でも、1 つ前の正常なレコードから復元できる。

## 保存タイミング

以下のタイミングで NVS への保存を実行する:

| タイミング | 説明 |
|---|---|
| スライド確定直後 | `commitGesture` でライフ変更が確定した直後 |
| Undo 直後 | Undo 操作でライフが復元された直後 |
| メニュー操作直後 | Rematch、Swap Sides 等のメニュー操作後 |

**スライド中の 1 ポイントごとには保存しない。** 外周スライド中にライフが 1 ずつ変化するたびに NVS 書き込みを行うと、書き込み回数が過剰になり NVS の劣化を早める。保存は指を離して変更が確定した時点で 1 回だけ行う。

## スキーマ互換性

`schemaVersion` フィールドにより、データ形式の前方・後方互換を管理する。

### 方針

| シナリオ | 動作 |
|---|---|
| 現行バージョンと同一 | そのまま読み込む |
| 旧バージョン（対応範囲内） | 読み込んだ後、現行バージョンへ移行（マイグレーション）する |
| 未対応バージョン（現行より新しい、または対応範囲外に古い） | **安全に拒否**し、新規ゲーム扱いにする |

**未対応バージョンのデータが存在しても起動不能にしてはならない。** 読み込めないデータは無視し、保存データなしとして正常に起動する。これにより、ファームウェアのダウングレード時にもデバイスが使用可能な状態を維持する。

## 将来フェーズ: LittleFS によるイベントログ

モバイル連携フェーズでは、試合イベントのログを LittleFS に記録する。NVS は頻繁な大容量ログの保存に向かないため、イベントログは LittleFS へ分離する。

### 役割分担

| ストレージ | 保存対象 |
|---|---|
| NVS | device_id、ペアリング情報、設定、現在の match_id、最後の sequence、現在状態の小さなスナップショット |
| LittleFS | 試合イベントログ、完了済み試合 |

NVS は小容量・低頻度の書き込みに適しており、デバイス設定や最新スナップショットの保持に使用する。LittleFS は動的ウェアレベリングを持ち、頻繁な追記操作に対する耐久性が高い。

### ファイル構成

```
/matches/
  active.log
  53ecb42d-....log
/index/
  matches.idx
```

| ファイル | 内容 |
|---|---|
| `/matches/active.log` | 進行中の試合のイベントログ |
| `/matches/<uuid>.log` | 完了済み試合のイベントログ（試合終了時に `active.log` からリネーム） |
| `/index/matches.idx` | 試合一覧のインデックス |

### PersistentEventRecord

```cpp
struct PersistentEventRecord {
    uint16_t magic;
    uint8_t schemaVersion;
    uint8_t flags;
    uint32_t recordLength;
    uint64_t sequence;
    uint8_t payload[];  // CBOR event payload
    uint32_t crc32;
};
```

| フィールド | 型 | 意味 |
|---|---|---|
| `magic` | `uint16_t` | 有効なレコードの識別子 |
| `schemaVersion` | `uint8_t` | イベントレコードのスキーマバージョン |
| `flags` | `uint8_t` | レコードの種別フラグ |
| `recordLength` | `uint32_t` | レコード全体の長さ（バイト） |
| `sequence` | `uint64_t` | イベントの通し番号 |
| `payload[]` | `uint8_t[]` | CBOR エンコードされたイベントデータ |
| `crc32` | `uint32_t` | レコード全体の CRC-32 チェックサム |

### 起動時の復元

起動時はログファイルの先頭から CRC を検証し、破損レコード以降を切り捨てる。破損レコードより前の有効なイベントはすべて復元される。

### 書き込み順序

モバイル連携フェーズでの書き込みは以下の順序で行う:

1. コマンド/ジェスチャーの検証
2. イベント生成
3. LittleFS へ追記
4. flush（ファイルシステムへの書き出し確定）
5. RAM 状態へ適用
6. NVS スナップショット予約
7. 画面更新
8. BLE 通知

この順序により、flush（手順 4）が完了した時点でイベントは永続化されている。手順 5 以降で電源が落ちても、次回起動時にログファイルからイベントを再生して RAM 状態を復元できる。

### 保持ポリシー

- 直近 100 試合またはログ領域の 80% まで保持する
- 未同期試合（スマートフォンへの転送が完了していない試合）は自動削除しない
- 容量不足時は最も古い同期済み試合から削除する

詳細は [モバイル連携設計](./10-mobile-integration.md) を参照。

## 電源断に対する設計

どの時点で電源が落ちても、次回起動時にデバイスが正常に起動できることを保証する。

### MVP での保証

| 電源断のタイミング | 結果 |
|---|---|
| スライド中（未確定） | スライド前の状態が復元される。未確定の変更は失われる |
| `commitGesture` 完了後、NVS 書き込み前 | 1 つ前の保存時点の状態が復元される。最後の 1 操作が失われる |
| NVS 書き込み途中 | 書き込み先のスロットが破損する。前のスロットの正常なレコードから復元される |
| NVS 書き込み完了後 | 最新の状態が復元される |

### 将来フェーズ（LittleFS）での保証

| 電源断のタイミング | 結果 |
|---|---|
| LittleFS 追記前 | 最後の 1 操作が失われる |
| LittleFS 追記途中 | 破損レコード以降が切り捨てられる。それ以前のイベントは復元される |
| flush 完了後、RAM 反映前 | ログからイベントを再生して RAM 状態を復元する |
| NVS スナップショット更新途中 | ログからの再生で補完する |

テスト観点の詳細は [テスト戦略](./11-testing.md) に委ねる。

## 要検証事項

以下の項目は設計段階では確定しておらず、実機での検証が必要である:

- **LittleFS の電源断耐性**: 書き込み途中での電源断テスト（抜き差し試験）が必須。LittleFS は電源断耐性を持つとされるが、ESP32-S3 + M5Stack StopWatch の組み合わせでの実動作は未検証
- **Flash 書き込み寿命の見積もり**: 16MB Flash の書き込み耐久回数に対して、1 試合あたりのイベント数・試合数から実用上の寿命を見積もる必要がある。この見積もりは未検証
- **NVS 16 スロットローテーションの十分性**: 16 スロットで NVS の劣化を十分に抑制できるかは、書き込み頻度の実測データに基づいて判断する必要がある
